# Toolchain

Everything runs in Docker (`tools/docker.sh <cmd>`). The image is built natively for the Docker host (`linux/arm64` on Apple Silicon, `linux/amd64` elsewhere; see "Native image" below). Never install tools on the host.

## Pinned versions (tools/Dockerfile)

The Docker image pins `splat64` 0.50.0, `spimdisasm` 1.42.4, `rabbitizer` 1.16.2, `pycparser` 3.11, `colorama` 0.4.6, `m2c` (git commit `708d2d2`), `PyYAML` 6.0.3, `tqdm` 4.67.1, `crcmod` 1.7, `ninja_syntax` 1.7.2, `binutils-mips-linux-gnu` 2.38, `ninja` 1.10.1, `make` 4.3, `git` 2.34.1, `maspsx` `e85ecb3`, `objdiff-cli` v3.8.2, `mkpsxiso`/`dumpsxiso` 2.30, `p7zip-full` `16.02+dfsg-8`, and `mame-tools` (`chdman`) `0.242+dfsg.1-1` (T-3300, for `tools/identify_version.py`; `amd64` and `arm64`). Compiler and matching tools live in `/opt/`: `decompals/old-gcc` 0.17 in `/opt/gcc/<ver>/` (`amd64` image only, covering `2.6.3-psx`, `2.7.2-psx`, `2.7.2-cdk`, `2.8.0-psx`, `2.8.1-psx`, `2.91.66-psx`, and `2.95.2-psx`), `decompals/ido-static-recomp` v1.2 (commit `9c242ad`) in `/opt/ido/5.3/` and `/opt/ido/7.1/`, `asm-processor` (simonlindholm) `f3b2f85` in `/opt/asm-processor`, and `decomp-permuter` (simonlindholm) `8556c81` in `/opt/decomp-permuter` with `toml` 0.10.2 and `Levenshtein` 0.27.1 (T-1330). Environment variables are `MASPSX_DIR=/opt/maspsx`, `GCC_DIR=/opt/gcc`, `IDO_DIR=/opt/ido`, `ASM_PROCESSOR_DIR=/opt/asm-processor`, and `PERMUTER_DIR=/opt/decomp-permuter`.

## Native image (T-3310)

Before T-3310 the image was forced to `linux/amd64`, so on Apple Silicon every build ran under Rosetta/QEMU. Game code needs no x86-only tool, so the image is now built for the host architecture.

- `tools/docker.sh` queries the Docker daemon for its architecture and selects `linux/arm64` or `linux/amd64`. `TOKIMEMO_PLATFORM=linux/amd64` (or `linux/arm64`) overrides it. The image is named `tokimemo-decomp` on `amd64` and `tokimemo-decomp-arm64` on `arm64`, so both can exist side by side (`IMG` still overrides the name). The Dockerfile hash label is kept, and the check also compares the image's OS and architecture so a wrong-architecture image under the same name is rebuilt.
- For IDO, `amd64` uses the upstream v1.2 release binaries, while `arm64` runs `make RELEASE=1` from the same commit (`9c242ad`, `IDO_REV` in the Dockerfile) with the flags upstream uses for its releases. The Dockerfile builds IDO 5.3 and 7.1 this way (taking about 10 minutes on a loaded laptop, once per Dockerfile change). `ugen` 5.3 gets `--conservative` from the upstream Makefile.
- A clean build on the native image and on the `amd64` image produces byte-identical `.bin`/`.elf`/`.ok` files (27 of 27 SHA-1 OK on both) and 537 byte-identical objects. The single exception is architecture-independent, where `asm-processor` writes a random temporary directory name (`/tmp/asm_processorXXXXXXXX/preprocessed_<md5>.c`) into the `.mdebug` string table; masking that string makes all objects equal. A direct IDO check compiled 40 sources (every 11th file of `src/`, with `INCLUDE_ASM` lines removed) using IDO 5.3 and 7.1 at `-O0 -O1 -O2 -O3` (320 compiles). Both images produced identical object hashes, whereas `-g` output differs on every run on either architecture due to timestamps and cannot be compared. Note that `-O3` writes `x.u` into the current directory, so concurrent runs in one directory crash `uld`.
- The `arm64` image omits `mkpsxiso`/`dumpsxiso` (upstream ships `x86_64` builds only, and `tools/extract_disc.py` replaces `dumpsxiso`) and the `old-gcc` versions other than `2.7.2-psx` and `2.8.1-psx` (see "Old gcc on arm64" below). Run `TOKIMEMO_PLATFORM=linux/amd64 tools/docker.sh ...` to build and use the full `amd64` image under emulation when needed.

## Windows hosts (T-10700)

- Use Docker Desktop with the WSL2 backend and run `tools/docker.sh` from Git Bash. If the Docker CLI is not on the Git Bash `PATH` by default, add `export PATH="$PATH:$LOCALAPPDATA/Programs/DockerDesktop/resources/bin"` (per-user install) or `/c/Program Files/Docker/Docker/resources/bin`. Docker Desktop must be running (`docker version` shows a server).
- Under MSYS (`uname -s` matching `MINGW`/`MSYS`/`CYGWIN`), `docker.sh` sets `MSYS_NO_PATHCONV=1` and passes the repo as `pwd -W` (`C:/...`); otherwise MSYS rewrites `-w /work` into `C:/Program Files/Git/work` and Docker refuses it. `TOKIMEMO_SCRATCH` is converted the same way.
- The `old-gcc` `cpp` binary is 32-bit, so on the bind mount `stat()` fails with `EOVERFLOW` (64-bit inodes). `tools/cc.py` (`run_cpp`) then reruns it on a `/dev/shm` copy of `include/` and the source under the same relative paths; where `cpp` works it runs in place.
- `.gitattributes` forces LF line endings so a Windows checkout runs unchanged in the container. The repository stays on the Windows filesystem (bind mount through WSL2); see the ticket for measured build times.

## Old gcc on arm64 (T-9200)

The release binaries of `decompals/old-gcc` are `x86_64` only. The `arm64` Dockerfile builds `cpp` and `cc1` of GCC 2.7.2 and 2.8.1 (the `-psx` targets) from the GNU tarballs (SHA-256 pinned) with the `old-gcc` patches (commit pinned, patches only). Both are GPL; nothing built is redistributed and no SDK binary is involved. The build steps follow `old-gcc`'s own Dockerfiles, with four adjustments for an `arm64` (LP64) host:

- No `-m32` host flag is used; `old-gcc`'s `xm-darwin.h` (a generic LP64 host description with 32-bit `HOST_WIDE_INT`) replaces `config/i386/xm-i386.h` after `./configure --host=i386-pc-linux`.
- GCC 2.7 and 2.8 call about a dozen pointer-returning functions without a declaration (`emit`, `expand_expr`, `remove_death`, `replace_regs`, `reorder_blocks`, `truthvalue_conversion`, and others). On a 64-bit host the `rtx` pointer is truncated to 32 bits and `reorg.c` crashes (`arith_operand` on a truncated pointer, found on `src/main/80053650.c`). A force-included header declares them, and `lookup` in `cexp.c` gets a declaration via `sed`.
- Standard libc prototypes are force-included (`stdlib.h`, `string.h`, `strings.h`, `alloca.h`) alongside `-fcommon -fno-strict-aliasing -w`.
- Only `cpp` and `cc1` are built because the driver references `sys_nerr` (removed in modern `glibc`) and `tools/cc.py` calls `cpp` and `cc1` directly.

For equivalence verification, GCC 2.7.2 output (`-O2 -G0 -mcpu=3000`) across 110 sources (every fourth file of `src/`, with `INCLUDE_ASM` lines removed) is byte-identical to the `amd64` release binary under emulation (110 of 110; before adding the prototypes, 1 crashed). The same check for 2.8.1 also matches 110 of 110. Pointer hash casts (`cse.c`, `varasm.c`, `tree.c`, affecting hash-table order only) are left untouched. Build time is about 2 minutes per version.

## Per-object toolchain (T-9200, T-24086)

`config/toolchains.txt` assigns a toolchain to single objects (main executable `main/<addr>` or overlay `<UNIT>/<addr>`, matching the splat `c` subsegment name). `configure.py` checks every name and form and passes the configuration to `tools/cc.py`. This is used for the PsyQ-GCC-built SDK modules linked into the ends of overlays (`TAIIKU/801488F0` `GsSetFogParam`, `TT/8014D260` `ratan2`); see [[gcc-objects]] for how those objects are identified and which functions they hold.

`tools/cc.py` runs `maspsx` with `--expand-div`, followed uniformly by `tools/sdk_aspsx_pass.py` (T-24086; tests in `tools/test_sdk_aspsx_pass.py`). That pass models three habits of the Sony NEWS-OS / MIPS workstation assembler (`as0` + `as1` derivative) measured across `asm/lib*.s` (`tools/aspsx_survey.py`, T-11890) and verified natively on `as0` + `as1` (T-24086):

1. `l* rd,sym(rs)` is expanded through `rd` when `rd != rs` (103/103 in `asm/lib*.s`).
2. `mflo`/`mfhi` is placed immediately after `div $zero,rs,rt` when `rd` is not read by the divide check sequence (`rd not in {rs, rt}` for signed `div`, `rd != rt` for `divu`; 4/4 in `TT:func_8014D260`, 63/67 in `asm/lib*.s`), with no `Reuse of` `nop` before an `rd` reader (16/16).
3. The two-slot `mflo`/`mfhi` hazard window is enforced before labels, GCC `.set noreorder` branches, and `mult`/`div` (290/290 in `asm/lib*.s`).

On `arm64`, `objdiff-cli` uses the v3.8.2 `linux-aarch64` release, while `binutils`, `gcc-mips-linux-gnu`, `ninja`, `make`, and Python packages use the Ubuntu 22.04 and PyPI `arm64` builds of the same versions (`binutils` 2.38). Timings and test results are in [[tickets/T-3310-native-docker-image]].

## Compiler choice

Game code (`src/main/*.c` and overlays) compiles with SGI IDO 5.3 using `cc -c -EL -O2 -mips1 -G 0 -non_shared -Wo,-nokpicopt -cckr -Xcpluscomm`, run through `asm-processor` so `INCLUDE_ASM` functions are spliced in and assembled with GNU `as` ([[tickets/T-0013-identify-original-compiler-pipeline]]). IDO accepts `-EL` and writes little-endian ELF. It reproduces the original codegen signatures that GCC could not (`$t6`-first temporaries, `$at` store expansion with the store in the `jr` delay slot, `lh` copies, `or` for move, `li` as `addiu`, and IDO's save-order prologues), allowing the first 23 leaf functions to byte-match immediately.

The `uopt` option `-Wo,-nokpicopt` stops `uopt` from keeping the address of a directly accessed global in a register, matching the original. Integer constants and array base addresses still live in registers (hoisted loop bounds, `li t1,0x44; multu`), also matching the original ([[tickets/T-0017-const-in-reg-loop-hoisting]]; it replaced `-Wo,-no_const_in_reg` from T-0014, which suppressed both). IDO 5.3 is not the exact original compiler because every non-empty stack frame in the original is 16 bytes larger than IDO 5.3's, which no IDO 5.3 or 7.1 option reproduces ([[tickets/T-0014-find-exact-ucode-compiler]]); the frame emulation pass below models that difference. See [[matching-notes]] for evidence and hypotheses. IDO 7.1 is installed for comparison; 5.3 matched one function that 7.1 did not (`func_8004E750`).

`configure.py` selects the toolchain per C file (`C_TOOLCHAIN`, `OVL_C_TOOLCHAIN`, and the per-object table `config/toolchains.txt`, T-9200, with the file list read from the YAML's `c` subsegments), and `tools/cc.py` supports `ido <ver>` and `gcc <ver> <aspsx>`. The GCC path (`cpp | cc1 | maspsx | sdk_aspsx_pass | as`, `-O2 -G0 -mcpu=3000`) is used for the PsyQ-GCC-built SDK modules in overlays (`TAIIKU/801488F0`, `TT/8014D260`) and is ready for any 1995-era PsyQ SDK library C ([[psyq-sdk]]). It uses the `old-gcc` compilers, which the `arm64` image builds for `2.7.2-psx` and `2.8.1-psx` (see "Old gcc on arm64"). `-G 0` is used everywhere because no code in the executable uses `$gp`.

## Assembler flags

Assembly runs `mips-linux-gnu-as -EL -march=r3000 -mabi=32 -G0 -Iinclude -I.`. IDO-built C runs through `asm-processor/build.py` (IDO `cc`, then GNU `as` for the spliced asm with prelude `include/asmproc_prelude.inc`), while GCC-built C runs through `cpp | cc1 | maspsx | sdk_aspsx_pass | as`. `tools/cc.py` checks every stage. The splat `INCLUDE_ASM` macro (`include/include_asm.h`) is used with `INCLUDE_ASM_USE_MACRO_INC` defined in `include/common.h`, so `include/macro.inc` supplies `glabel`/`nonmatching`.

## Frame-layout emulation pass (T-0016)

`tools/frame_pass.py` runs on every IDO compile. It models one measured difference between IDO 5.3 and the original compiler, where frames are 16 bytes larger. The extra 16 bytes sit above the register saves in functions that save `$ra` and below everything in functions that do not (see [[matching-notes]], section "Frame layout emulation" for rule, evidence, and limits). It is a toolchain emulation pass under `CODING_STANDARDS.md` section 7a (uniform, documented, evidence-backed, and with no per-function control) so ordinary C compiles to the original's frames.

IDO's internal pipeline runs `cfe`, `uopt`, `ugen`, and `as1` in sequence, where `ugen` hands `as1` a binary assembly file ("binasm", 16-byte records). `tools/cc.py` runs IDO with `USR_LIB` pointing at a temporary directory of symlinks to the real IDO files, except `as1`, which is a two-line shell shim calling `frame_pass.py --as1 /opt/ido/5.3/as1 ...`. The pass rewrites the `.frame`, `.mask`, and every `$sp`-relative immediate in the binasm records and then execs the real `as1`.

This layer was chosen over three alternatives. `cc -S` text cannot be reassembled to the same code because the listing drops the `vreg` records `as1` uses. The ucode route (`DEF Mmt` +16 between `uopt` and `ugen`) fixes non-leaf functions without touching offsets, but cannot express the leaf layout and misplaces the hole when spill temporaries exist. Operating on binasm records exposes `.frame`/`.mask` and instruction fields directly without decoding machine code. The pass is deterministic and fails with a build error (`frame_pass.py: ...`) on anything it does not understand. Run `tools/docker.sh python3 tools/test_frame_pass.py` for unit tests.

A real copy of the original compiler would replace the pass without any change to the C code ([[tickets/T-0100-older-mips-compiler-emulation]] stays open for that).

Table-copy functions whose local sits 4 bytes higher than plain IDO places it (`sp+0x2C` in a `0x90` frame instead of `sp+0x28` in `0x88`) are not part of the pass (T-3330). The cause is in the source, because IDO gives every declared local a stack slot once any local lives in memory, and the original declared one more scalar (the index) before the table. No pass or `cc.py` hook is needed; see [[matching-notes]], section "Local function-pointer tables". In addition, because `as1`'s prologue schedule depends on the source line layout, test C must be written one statement per line, matching `src/`.

## Differences with no pass (T-3001, T-5020, T-7020)

Three candidate differences were measured and left without a pass (details in [[matching-notes]], "Shared constants, shared `lui $at` and loop unrolling"):

1. The original's `uopt` sometimes keeps a constant in a register for several straight-line stores (124 sites against 1,052 reloads), which no IDO 5.3 option or C form reproduces under `-Wo,-nokpicopt`. Under T-7000 K&R promotion, constants of different types are not shared (one `li at,k` per compare of a `u8` and an `s32`), and a chain assignment to array or record elements keeps one register. Forty-one functions remain where the original keeps constants in `$t6`-style temporaries.
2. The original's `as1` reuses one `lui $at` for stores to different offsets of a symbol. Under T-25102, IDO 5.3's `as1` does share across offsets when the symbol is defined in the compiled C and both addresses fall in one 16-byte-aligned chunk of the section. By contrast, a symbol that the C sees as `extern` (such as an `INCLUDE_RODATA` piece) never shares; see [[matching-notes]] T-25102. Adding a synthetic pass for `extern` symbols would break matched functions whose C uses one base symbol to keep `as1` from hoisting loads (135 initially, rising to 221 with recovered aggregates). Because the original shares `$at` only for data that the sharing file defines, per-object data islands handle those cases (T-3052, T-9010).
3. Loop unrolling is not a compiler difference (T-7020). IDO 5.3 unrolls under the same conditions as the original. Observed differences come from the C, such as trip count, a counter assigned again later, nested or `goto` loops, pointer loops written where the original had index loops, or one-line loop bodies for load order. The original's lack of pointer-loop remainders shows its loops were index loops. `-Wo,-unrolllimit,N` below 200 changes matched functions and is not needed. `as1` schedules by source lines in both compilers (removing the `.loc` records changes 906 matched functions). See [[matching-notes]], "Loop unrolling and scheduling (T-7020)" and [[decompile-workflow]], "Loops: unrolled or not".

Under T-9000, the rows of [[data/t0018-cases]] were re-tested under K&R and clustered ([[matching-notes]], "T-0018 rows under K&R"). Twenty were source idioms (implicit `int`, bit-field stores, chain assignment) and matched; the rest are `uopt` coloring and constant-propagation differences that no ucode record exposes, so no new pass was added.

T-16910 rejected the T-16900 `cpw` rule (`zcopy` off plus constant first where a procedure copies a narrow signed global into a local and compares it with a constant). In the original, the coupled shape is one NAME_ENT family (7 functions, one byte), while constant-first compares on narrow signed globals occur in 15 more functions without a copy. The order follows aggregate membership (64 of 64 constant-first compares on aggregate members, 8 of 8 variable-first on scalars). IDO produces that order from C that reads through the aggregate, making it a data-type matter; see [[matching-notes]] ("Constant-first compares follow aggregate membership", T-16910). Under T-16920, the 7 functions matched as C by reading the field through a local `GameState *g` (an indirect load), needing no pass.

## K&R mode (T-7000)

`-cckr` runs IDO's front end in K&R mode (`cfe` `-std0`, no `__STDC__`). Under K&R rules, `unsigned char` and `unsigned short` promote to `unsigned int`, so plain C on a `u8`/`u16` value compares, shifts, and divides unsigned (`sltiu`, `srl`, `divu`), matching the original in 1,459 of 1,462, 556 of 556, and 101 of 105 cases. In addition, a narrow parameter passed to a callee without a prototype is converted in place at entry (`andi t6,a0,0xff; move a0,t6`), while prototypes still apply where declared. IDO's K&R front end drops the widening `CVT` of unsigned narrow loads, which the original kept for global variables; `tools/cvt_pass.py` restores it (next section). See [[matching-notes]], "K&R promotion rules (T-7000)".

## The original compiler (T-3100)

See [[original-compiler]] for identification, evidence, and citations. The closest fit is a MIPS/SGI ucode suite at release 3.18, shipped by SGI as IDO 5.2 (March 1994), one minor version before our IDO 5.3 (3.19). The evidence comes from the linker version stamps in `O.BIN`, where `a.out` `vstamp` and symbolic-header `vstamp` are both `0x0312`. The link was a little-endian ECOFF link on a big-endian host, fitting the Sony NEWS-based PlayStation toolchain (UNVERIFIED). The `O.BIN` procedure descriptors show that the 1995-07-25 developer build already had the `+16` frames, supporting the frame pass as a compiler property.

`-Wo,-regr,N` (an undocumented `uopt` option for the caller-saved register pool) was tested and rejected because it moves switch selectors to `$v1` without promoting the global and regresses 194 of 1,647 matched functions. IDO 5.3 does promote globals in straight-line code, only at a higher reference count than the original; the rules for [[tickets/T-1321-register-promotion-build-step]] are in [[original-compiler]] section 5. No IDO older than 5.3 is in `decompals/ido-static-recomp`; running IDO 5.2 or 4.1 (hosted by decomp.me under `qemu-irix`) requires user authorization under the licensing rule.

## IDO 5.2 and 4.1 (T-3110)

IDO 5.2 and 4.1 were tested privately with decomp.me's archives under `qemu-irix` ([[ido-52-evaluation]]; never committed and not part of the build). IDO 5.2 writes the `O.BIN` stamp 3.18 but otherwise generates the same code as 5.3: with the frame pass, all 2,564 matched C functions are identical, and without it, 5.2 produces 5.3's frames. IDO 4.1's `ugen` produces the original's `+16` frames natively: with 5.2's front end and `uopt`, its frame size and `$sp` offsets equal the frame pass's across all 2,564 functions, providing real-compiler evidence for the pass. Its older register allocation, however, breaks 80 of them, and neither version reproduces the T-1321 unsigned-load and switch-temporary behaviors. The project therefore keeps 5.3 + frame pass + `cvt_pass.py`. The evaluation harness is `tools/ido_eval.py`.

T-20700 repeated the 4.1 back-end test after the K&R `cfe` and `tools/cvt_pass.py` front end landed. IDO 4.1's `as1` changes 1 of 6,336 matched functions (padding an `mflo`/`multu` hazard with `nop`s where 5.3's `as1` and the original fill it), matches no sched/hoist draft, and still requires the same one-line `FAKE` tricks. IDO 4.1's `ugen` changes 1,355 matched functions (unaligned-store expansion, in-place register reuse, no K&R parameter copy) and matches one draft (TACO `func_8013B2A0`), while its frames equal the frame pass's in 6,335 of 6,336 functions. No build step was adopted from `as1` ([[ido-52-evaluation]], T-20700 section).

Under T-20710, IDO 4.1's `ugen` also matches the original's block-copy state (a struct copy after a loop or conditional block stays in state B, whereas 5.2 and 5.3 switch to F), closing 6 census cases of [[data/true-gaps]]. While 4.1's `ugen` binary as a whole changes 1,307 matched functions, its exact block-copy state rule was later modeled in `tools/ugen_pass.py` (T-24092 and T-26000 below); see [[ido-52-evaluation]], section "T-20710" and reproducers in `tools/ido_eval_cases/ugen_copy_state/`.

## Unsigned-load conversion pass (T-1321, T-5010, in the build)

`tools/cvt_pass.py` wraps IDO's `uopt` on every IDO compile (via a shim under `USR_LIB`, like the `as1` shim of the frame pass; `tools/cc.py` `SHIMS`, with `cc.ido_frame_env(ver, tmp, {"uopt": None})` to disable it in an experiment). T-1321 initially kept it out of the build because it changed 26 matched functions; T-5010 added the entry and compare rules below and identified the source property behind the rest (unit-private data), so it changes zero matched functions. It models two measured differences in how the original compiler optimized global variables ([[matching-notes]], section "Unsigned-load conversion pass (T-1321)"):

1. IDO's ANSI `cfe` writes every load of an unsigned 8/16-bit variable as `LOD L` + `CVT J<-L`. `uopt` then allocates the widened value as its own expression, leaving the global with too few uses to stay in a register. The original instead keeps such a global in one register across blocks and calls (compare chain in `$v1`, reloads after calls into `$v1`). Before `uopt`, the pass deletes the `CVT` after a `LOD` of a global (memory type `S`) that the file accesses only as unsigned and narrower than a word. It preserves IDO's `==`/`!=` operand order (`uopt` swaps the operands when the left one is not a plain variable; the pass reorders the ucode to match the order IDO picks with the `CVT`, and keeps that one `CVT` when no order works). After `uopt`, it restores the unsigned load type (`lbu`/`lhu`) and puts constants first in `==`/`!=` against those globals, matching the order IDO produces with the `CVT`.
2. A `switch` whose selector is an unsigned global (`LOD L` of an `S` variable) is compared through a compiler temporary (`VREG`). The original keeps that temporary separate from the global (global in `$v1`, temporary in `$v0`, with the copy dropped when the temporary is dead), whereas IDO's global copy propagation merges them and puts the global in `$v0`. For each procedure with such a temporary, the pass inserts an `OPTN 405 0` record (`uopt`'s `zcopy` option, equivalent to `-Wo,-zcopy:0`) before its `ENT`, while every other procedure gets `OPTN 405 1`. Under T-24929, after `uopt` runs, in each of those `zcopy`-off procedures the compares of the chain that read the temporary's register are rewritten to read the global's register. That rewrite propagates the entry copy (`lod Rg` and `str Rt`) up to the first label, call, or store while keeping the copy itself. `as1` already does this in most such chains, except when the global's register is redefined in a case body while the temporary is live, which had left ETC `func_8013CCE4` on `$v0`. This refinement fires in 267 procedures, changes only `func_8013CCE4` (now matched), and keeps 27/27 SHA-1 ([[matching-notes]] T-24929).
3. Under T-5010, both rewrites apply only to a variable that the procedure loads or stores before its first call, branch, or label (`f(); switch (D)` and a switch inside an `if` keep IDO's `$v0` code). In addition, the `CVT` is removed only where the widened value is compared or switched on, keeping it for assigned, passed, or computed values; see [[matching-notes]], "Selector register rule (T-5010)". T-20610 measured refinements of this entry rule for globals first touched later (stored; compared with a non-zero constant; stored and compared with a constant; constant-first by the latest register definition). None were adopted because the narrowest gained one function while the others regressed 4 to 18 matched functions ([[matching-notes]], "T-20610").

Since T-7000, the pass starts with a widening step. The build runs IDO in K&R mode, whose front end writes no `CVT J<-L` after a load of an unsigned narrow variable. The step inserts `CVT J<-L` after every such load of a global (memory type `S`, 1 or 2 bytes), including for a switch temporary. It skips the insertion when the value goes directly into a store, a conversion, an array index, `++`/`--`, a truth test, an operand swap, or a narrow parameter. That matches where IDO's ANSI front end writes it (checked across all 440 C files: 1,711 loads, where the 28 differences all have an explicit unsigned operand in C). Locals and parameters keep IDO's K&R form, as in the original. See class `Widen` and `test_compare_after_a_call_keeps_widened_value` in `tools/test_cvt_pass.py`.

The rules are uniform with no per-function control; the C controls the output just as in the original (`switch (D)` on an unsigned global gives `$v1`, while `u8 mode = D; switch (mode)` gives `$v0`). The one case the pass cannot see is unit-private data (a variable used by only one overlay or file), which the original did not promote; such functions switch on a local copy marked `FAKE` (16 in the matched set, T-5010). Unknown ucode or an operand the pass cannot move aborts the build (`cvt_pass.py: ...`). Run `tools/docker.sh python3 tools/test_cvt_pass.py` for unit tests (synthetic ucode records plus snippets compiled by IDO). The ucode record layout comes from the `ido-decomp` sources (`src/ucode.h`, `src/libu/uini.c` of `n64decomp/ido`); no SGI code is used or committed.

## Block-copy state pass (T-24092; IDO 4.1 rule since T-26000)

`tools/ugen_pass.py` wraps IDO's `ugen` on every IDO compile and places a zero-register sentinel before each `Umov` so the copy compiles in state B (two scratch registers spent before the end or transfer register) or state F (one). See [[tickets/T-24092-ugen-block-copy-state-pass]] for the root cause and the IDO 5.3 difference.

Since T-26000, the pass implements the rule that IDO 4.1's `ugen` follows across the 30 cases in `tools/ido_eval_cases/ugen_copy_state/` ([[ido-52-evaluation]], "T-25608: 4.1 ugen on the rule candidates"). Each procedure is walked in ucode order:

- It starts in B, with nothing carried over from the previous procedure.
- An indirect store (`Uistr`/`Uistv`) sets F.
- A `Ufjp`/`Utjp` that tests a compare (`equ neq les leq grt geq`, including under `Ulnot` or after `Urstr`) of two operands that are not `Uldc` sets B, because `ugen` compares two registers there (`bne a1,t7`, `slt`, and a branch).
- Everything else preserves the current state, including branches on any other value, `Uujp`, `Uxjp`, `Uijp`, calls, direct stores, labels, and the copies themselves. Compares with a constant on either side also preserve the state (`beqz`, `blez`, `slti`, `li at,3; beq`; `uopt` sometimes writes `x != 0` as `ldc 0; x; neq`, and 4.1 preserves the state there too, per the T-26000 fix round).

A branch whose condition record is missing or is not an expression, or a compare with fewer than two operands, aborts the compile (`PassError`). Tests in `tools/test_ugen_pass.py` cover the 30 cases as synthetic ucode plus the rule's components; end to end, the real `uopt` output of all 30 case files gives 4.1's state, including the T-26000 cases with the constant on the left (`copy_ne0_left_if`, `copy_store_then_ne0_left_if`, `copy_store_then_eq0_left_if`).

In the full-build census (2026-10-23, 566 procedures with a `Umov`), compared against the T-25608 rule only main `strCallback` (F to B) and `func_8005938C` (FFF to BBF) changed (both previously `FAKE`-steered for the old detector), while main `func_8006B0C8` stayed BBBB. After re-steering those two without new `FAKE`s (spellings in [[matching-notes]], "T-26000") and removing the empty-test `FAKE`s of main `func_80054FC0` (T-25105) and TACO `func_80145650` (T-25136) that existed only for the old detector, all 27/27 binaries matched.

The first version of the T-26000 rule counted a compare with the constant on the left as a register compare (B). With an indirect store before it, 4.1 keeps F there (`copy_store_then_ne0_left_if`, `copy_store_then_eq0_left_if`), and the pass now does the same; across the 566 procedures, none changed state and the build remained 27/27.

Three known limits remain where the pass and 4.1 differ ([[ido-52-evaluation]] "T-26000"):

- IDO 4.1's `ugen` also sets F at a branch on a value that is not a compare (`if (G & 1)`, `if (p[1])`, a one-bit field, `>>`, `%`, `|`, `+`), whereas the pass keeps the state there. Modeling that behavior would explain `strCallback` and `func_8005938C` without their never-true arms, but it puts the compaction copy of `func_8006B0C8` (after a one-bit field test) in F, where the original is B.
- IDO 4.1 (and 5.3's raw `ugen`) ignores a store in an arm that `ugen` drops as never entered (`if ((unsigned)G < 0) { *(u8 *)0 = 0; }`, `copy_dropped_arm_store`: B; the same store in a live arm, `copy_live_arm_zero_store`: F). The pass counts it, and the never-true `FAKE` arms rely on that in main `strCallback` and `func_8005938C` (T-26000) and MASTER `func_801344E0` and `func_801363F4` (T-25107).
- Stored compares (`x = a < b;`), `Uxjp` (`switch`), and `Uijp` were not measured in 4.1.

## Jump tables and asm-processor (T-1340)

`asm-processor`'s `.rodata`/`.late_rodata` support lets `INCLUDE_ASM` functions and compiler-emitted jump tables share one object by making the compiler emit dummy data in the right order and replacing it with the asm bytes. `tools/rodata_pieces.py` writes those sections into the function files; see [[build-system]].

## Shift-JIS string literals (T-0500)

C sources are UTF-8 so Japanese strings stay readable in `src/`. `tools/cc.py` (`sjis_literals`, tests in `tools/test_cc.py`) re-encodes every non-ASCII character inside a string or character literal to its Shift-JIS bytes as octal escapes before IDO sees the file (compiling `<obj>.sjis.c`), matching the rule `tools/asm.py` applies to splat's `.asciz` lines. Raw Shift-JIS bytes would fail because a second byte `0x5C` (`表`) is parsed as a backslash by `cfe`. Non-ASCII text outside a literal stops the compile (comments are ASCII per `CODING_STANDARDS.md` section 9). This is an encoding step rather than an emulation pass; the emitted bytes are those of the literal as written.

## Object padding pass (T-0012)

`tools/cc.py` zero-pads the `.text` of every compiled C object to a multiple of 16 bytes (function `pad_text`, unit tests in `tools/test_cc.py`). This is a uniform toolchain emulation pass under `CODING_STANDARDS.md` section 7a, modeling the original link that aligned every object's `.text` to 16 bytes while our linker script uses `SUBALIGN(2)` to pack the SDK asm objects.

In the main executable, 804 of the 833 gaps between adjacent game functions are zero, and the 27 non-zero gaps all end on a 16-byte boundary and consist of 4 to 12 zero bytes ([[source-files]]). With the pass active, a file whose last function is in C reproduces that padding (`func_80043504` matched as an empty C function). Functions kept as `INCLUDE_ASM` already contain their trailing `nop`s, so nothing is doubled. A missing `.text` causes `objcopy` to abort the compile. On a clean rebuild, the main executable and all 26 overlays match their SHA-1 hashes (27 of 27 OK).

## Trailing padding pass (T-1310)

`tools/trailing_pad.py` (called by `tools/cc.py` after every compile, before `pad_text`) restores the original's trailing zero words after each C function. Because the original link aligned each object's `.text` to 16 bytes, zero words after an object's last function sit in the middle of a multi-object C file. An `INCLUDE_ASM` function carries them (splat prints them after `endlabel`), whereas a C function loses them. In addition, `asm-processor` requires at least 2 instructions per block, so the 1-nop case (end address = 12 mod 16, occurring in 124 overlay functions) could not use a stub, and the old `INCLUDE_ASM("src/ovl/pad", ...)` stubs (T-0700) required per-site source lines.

Under `CODING_STANDARDS.md` section 7a (uniform, no per-function control, no source markers), for every function symbol that the source defines in C (not named by an `INCLUDE_ASM` line), the pass reads `asm/{matchings,nonmatchings}/<segment>/<name>.s` (`asm/ovl/<NAME>/...` for overlays, `asm/.../main/<addr>` for `src/main/<addr>.c`). It counts the `nop` lines after the function's `endlabel` as the original's padding and inserts that many zero words at `symbol value + size`. Before inserting, it drops the assembler's own end-of-`.text` alignment fill (which belongs to no function; `pad_text` restores the 16-byte object alignment afterwards). Any unknown condition aborts the build, including a function symbol without size, a symbol inside the function, `HI16`/`LO16` or other relocations against the `.text` section symbol, trailing lines that are not `nop`s, or an `.s` without `endlabel`. A symbol with no `.s` (a `static` helper) receives no padding.

The pass edits the relocatable ELF directly (updating symbol values, `.text` section symbol size, `REL` offsets, and in-place addends of `R_MIPS_32`/`R_MIPS_26` against the section symbol). Run `tools/docker.sh sh -c 'cd tools && python3 test_trailing_pad.py'` for tests (synthetic objects assembled and linked, compared byte-for-byte against sources with the `nop`s written out). The depfile lists every `.s` read so Ninja rebuilds when they change.

Across all `asm/**/{non,}matchings` function files, 392 functions have `nop`s after `endlabel`. Thirty are in the main executable (27 at the end of a `src/main` file, plus 2 odd 4/5-nop tails that are not 16-aligned), and 362 are in overlays (124 with 1 nop, 98 with 2 nops, 132 with 3 nops, and 8 with 4+ nops, where 11 end off a 16-byte boundary). Because the count comes from the data rather than an alignment formula, the odd tails need no special case.

As a related fix, `pad_text` also edits the ELF in Python because `objcopy --update-section .text=` with a longer section dropped every relocation of the object without warning (not hit earlier only because no object with relocations had needed end-of-object padding).

Under T-9600, `frame_pass.py` was clarified so a negative displacement on a tracked `sp + variable-index` register can cancel a positive index bias (used by SHOUGATU year/table addressing). It moves up by 16 with the local, just like positive local offsets. Direct negative `sp` offsets, including through plain copies of `sp`, remain unsupported. Synthetic binasm and real IDO `table[12*(year-95)]` tests cover the rule; see [[matching-notes]], "Tooling fixes, wave 8".

## uopt allocator diagnostics (T-9800)

The `-Wo,-zdbug:6` crash in `uopt` comes from an unimplemented guest `ecvt` wrapper in the pinned static recompilation. `tools/ido-ecvt.patch` repairs it for an external Docker build, and `tools/uopt_patch.py` adds diagnostic logging or isolated uniform allocator experiments without changing the Dockerfile or default compiler behavior. [[uopt-register-allocation]] documents the priority formula, register ordering, trace evidence, and full experiment scores. `-regr` also disables precoloring and special-cases 9, explaining its non-monotonic register pools.

Evaluation uses the existing `cc.py` pipeline, including the `cvt`, `frame`, and `trailing_pad` passes. `tools/uopt_eval.py` compares all 4,870 matched functions at the time and a fixed case corpus, while `tools/uopt_link_eval.py` also checks literal linked bytes, addresses, and whole-unit hashes. The 3.18 stamp identifies the compiler family and release, and the private IDO 5.2 evaluation showed that stock SGI 5.2 does not explain these allocation differences. Any new pass still requires every `CODING_STANDARDS.md` section 7a criterion and zero regressions; isolated case hits alone are insufficient.

Under T-9800, all eight uniform allocation candidates failed preservation. The best kept 4,209/4,870 literal linked function spans and 9/27 unit hashes while gaining one isolated case, and `a2`/`a3` preference gained two cases while keeping 3,653/4,870 functions and 5/27 units. No candidate was adopted. The stock control reproduced 4,870/4,870 functions and 27/27 units; full scores and coverage live in `wiki/data/t9800-allocator-scores.json`.

## Configured subobject text extent (T-10200)

After `cc.py`, `configure.py` runs `object_layout.py` uniformly for C objects. IDO and `cc.py` round `.text` size to 16 bytes, whereas a source split can lie on a 4-byte boundary. When that rounding alone exceeds the YAML subsegment span, `object_layout.py` removes the surplus zero tail only if no non-section symbol or relocation occupies it. Any other size mismatch is left for comparison and checksum verification, and instructions are never rewritten. BUNKASAI's `80154018` boundary uses this to own its orphan jump tables in C, extending the section-layout model without changing compiler flags. Synthetic ELF tests cover rejection of nonzero tails, symbols, and relocations; see [[build-system]] and [[tickets/T-10200-orphan-jump-tables]].
