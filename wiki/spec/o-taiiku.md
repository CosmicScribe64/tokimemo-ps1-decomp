# Sports festival overlay (TAIIKU)

TAIIKU is the project's overlay name for `sports_festival` (`GLOSSARY.md`). The code contains scene scripts, race/controller animation systems, talk events, resource loaders, and shared actor/display routines. Labels “A”, “B”, and “C” below refer only to three source clusters; this pass did not establish their in-game titles. The proposal table contains body-backed names for all 213 function definitions; nonfunction rows are limited to supported types, fields, data, locals and parameters. Opaque game meanings remain unresolved where the body does not establish them.

## Concrete scene flow observed

### Folk dance: `folk_dance_scene.c`

The mode-step switch begins by loading the audio bank, resetting the scene, clearing talk/actors and seeding `rand()` from the game timer. After the bank is ready, it scans all 11 girl records for `flags.f.met == 1`. With fewer than three eligible girls it writes `D_80122ECC = 2`. Otherwise it schedules a background read, selects two nonzero distinct girls, then initializes `[GIRL_SHIORI, girlA, girlB]` (`GIRL_SHIORI == 0`) and performs `rand() & 0x1F` swaps between arbitrary slots 0..2. Shiori begins at slot 0 but may occupy any final slot; portrait, current-girl, talk and event-log behavior use the resulting shuffled order. Once the background read completes it initializes the actors/background, starts music and reads the selected girl's portrait. Later steps set talk tables and speaker groups; the group number depends on `girl_state_rank`: ranks 0–1 use `girl * 3 + 5`, ranks 2–3 use `girl * 3 + 6`, and rank 4 uses `girl * 3 + 7`. The callback rows record the observed terminal steps; the meaning of the resulting dialogue/success labels remains unresolved.

The folk-dance log writer `sports_folk_dance_log_append` appends one event-log row for each of the three participant-list entries, with event scene ID 0x13 and current date/weekday. The initial list starts with Shiori (girl 0), but the three entries are shuffled before this call, so no final slot is fixed to Shiori. The final slot-2 entry is assigned rank 4 when its syoushin is at least 0x4C; event-log count saturates at 0xFE when its post-increment value reaches 0xFF. Its sole call is in `folk_dance_scene.c` mode-step case 2, after CD readiness during initialization and before portrait/dialogue setup. The purpose of this rank override is not identified.

The runner cluster begins at `sports_runner_race_mode_dispatch`, which indexes the ten-entry stage table by `mode_stage`; `sports_runner_race_resource_setup` performs the resource/readiness setup. `sports_runner_race_phase_one` is the first active race phase (0x5B-frame wait, audio-bank load, runner updates until position high-half 0x140); `sports_runner_race_phase_two` advances the next phase and changes the visible actor/text arrangement at 0x280. The latter waits for completion and applies table-driven X/Y deltas. These callbacks establish phases but not a complete placement formula.

## Runner source cluster A: `runner_race_dispatch.c`

`sports_runner_race_mode_dispatch` dispatches `D_8014933C[game_state.mode_stage]`. The setup function `sports_runner_race_resource_setup` resets scene/actors, seeds tpage slots, copies fixed lookup tables, requests sectors `0x1E` and `0x1F`, and waits for both fade completion and CD readiness before installing the next data set and advancing `mode_stage`.

The next observed routine, `sports_runner_race_phase_one`, waits for fade-in, then 0x5B VBLANK ticks, starts audio/bank loading, and enters its active step. The active step initializes runner records, updates runners and actors, and advances a 16.16 position/camera word by `0x18000` each tick. A threshold at high-half `0x140` advances stage. The following routine (`sports_runner_race_phase_two`) begins another phase: it advances the same position by `0x18000` per update, scrolls two display regions, and runs runner/actor updates. At high-half `0x280` it changes actors and prints two table-selected strings; then step 1 runs until `player.unk_01 != 0`; step 2 waits for `sports_runner_finish_actor_slide_update(0)` to report completion, then applies table-selected X/Y deltas and advances stage. This is concrete phase/camera behavior, but the exact race objective and final winner formula are not proven by this slice.

`SportsRunnerA` is a 0x24-byte record. The result updater `sports_girl_scene_result_update` uses the result bytes `D_801499D4[0..1]`: the first zero branch adds tokimeki 4 to each of 13 girls and another 2 plus affection 10 to the selected girl; if only the second byte is zero, it adds tokimeki 2 to all and another 1 plus affection 5 to the selected girl.
