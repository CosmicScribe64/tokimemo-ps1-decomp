## T-19001: TAIIKU package w3-d-p01 (80140810.c)

[[tickets/T-19001-w3-d-p01]], direct package of wave 3: one function, `func_80140A90` (2,020 bytes), the guarded draft from [[tickets/T-16554-pt-taiiku-p4]]. Not matched; the guarded draft keeps its 33 differing instructions (66 diff lines). Time: about 50 minutes. The siblings tool found no matched function above ratio 0.70, and `autotweak` (150 s, 686 edits) found nothing.

What this pass added is a measured model of the block copy's temporaries, from about 80 variants of the real function and about 120 isolated contexts in a scratch harness (not committed):
- **Method.** An isolated function `test(u8 *p, s32 n) { <context> *(R *)(A + 0x1a08) = *(R *)(A + 0x1980); }` with `R` a 17-word struct, compiled with `/opt/ido/5.3/cc -S` (0.3 s) so the listing shows ugen's own registers and its `.set noat` lines. The real unit was also compiled with an extra `ugen` shim (`cc.ido_frame_env(..., extra_shims={"ugen": ...})`) that saves ugen's input, which `cvt_pass.parse` prints as ucode. Both reproduce the 66-line miss of the real function.
- **The copy takes its address registers and its end register from ugen's rotating temporary list** (the T-16563 closer pass called it first-in, first-out; the rotation fits both). Between the two address registers and the end register it consumes either one entry (state F: end = source + 2 in the list, two `.set noat` lines in the listing) or two (state B: end = source + 3, one `.set noat` line). The draft is F, the original B. The position in the rotation does not matter (all ten start registers give the same state in the same context). After the copy the destination, source and one helper register stay busy for a while: the original's later temporaries run `$t9`, then `$t3`, `$t4`, `$t5` (rows 384, 398, 422, 453) and skip `$t0`..`$t2`, and the draft's run through the same order one step earlier (`$t8`, `$t9`, `$t3`, `$t4`). So the miss is one extra rotation step inside the copy, and everything after it follows.
- **State rule found.** Function entry starts in B. A store to a global symbol or to a stack slot (`str`, `rstr`) gives B. A store through any other base register (`istr`: `p[3] = 0`, `arr[n] = 0`) gives F, and so does a loop whose back-edge opens a new block (a pointer-store loop, a loop with the global store hoisted out). A call leaves the state as it is. A conditional block starts in F: `if (n) f();` gives F, `if (n) g = 0;` gives B (the store is in the block), `if (n) {}` stays at the entry state. Register-only code does not change it (`i = 2;` after the loop survives uopt and as1 as one extra instruction, and the state stays F). Tails like `D_8014A064 = 0;` between the loop and the copy give B (the original's numbering) but add an instruction.
- **Nothing in C reaches B after the loop without adding code.** Tried at the copy site, each with the loop code unchanged or the state unchanged: `for` / `while` / `do while` / `!(i == 2)` / `i != 2` / `i += 1` / count-down loops, index and pointer loops, the loop on one source line with the copy, eight copy spellings (`DisplayActor44`, `DisplayRecord44`, `TaiikuScene44`, `TaiikuActor44`, separate-symbol views, byte-address casts, `volatile` views; cfe emits `mov` in all of them, never `movv`), 20 statements after the loop (13 emit no code: `(void)i`, `if (i) {}`, `switch (i) {}`, `goto L; L:;`, a label, `while (0) {}`, a dead block local; the others add one instruction), a bit-field `|=` in the loop, and six forms of the tail store that might add a temporary. None changes the state. Only a global store between the loop and the copy does, and it adds an instruction.
- **The original is not the same machine as our ugen.** Matched twins show B after a global store (ETC `func_80137A14`, DATE `func_801572E4`), but SHUGAKU `func_801357AC` (same four byte stores, same copy, T-9330 row) has F in the original after them, and MASTER `func_801344E0`, `func_801363F4` and ENDING `func_80134270` show F after global byte stores in the original listings (asm scan; our compiler's state for them was not measured). So the state is not a function of the C context alone in the original; this fits the "older frame layout, newer register allocation" ugen of [[ido-52-evaluation]], not a source property. Nothing further can be done from C; a test needs the older ugen builds of that page.
- Two small facts for the next probe: the draft's `i` lives in `$a0` and its dead initial `move $a0,$zero` is deleted by as1, so a `$t` register held by uopt for it is not the cause (making `$a0`..`$a3` live across the loop only moves the dead initial move to `$v0` and changes nothing); and a uopt-held `$t2` is not visible anywhere in the original's listing (`$t2` is an ordinary ugen temporary at row 493).

- **`func_8014616C`** (3 rows, guarded, FAKE): the plain draft is 242 rows off because IDO promotes the frame counter `D_800E6280.unk_1104.w` into `$v0` for the whole function (compare chain, `or s0,v0,zero`) and restores it after every arm's call; the original reloads it once, at the end. Details and negatives in [[data/t0018-cases]]. A separate `D_800E7384` symbol for the final `+= 1` matches the whole function (1,512 bytes) but `migrate_globals --check` rejects the old name; the absolute-address read of the final value keeps the aggregate and leaves 3 register rows (`$v0` against `$t1`/`$t2`). `func_80146754` (not in this package) has the same shape.

Idioms: an absolute address gives a different expression to uopt than the symbol (no CSE or promotion with the variable), which fixes both the `lui t9; lw v1` pointer and the counter restores; combine it only once per function, since two uses share a `lui/ori` constant in `$v0`.

**Closer pass (Opus, about 30 minutes): `func_8014616C` stays a 3-row draft.** regdiff on the FAKE draft: the counter's range (`D_800E6280/unk_1104/w`) has 26 uses and 1 def over 26 units. The def is the final store, so the last block stays in the range and the sum takes `$v0`. The original's last block is plain ugen code. That needs a direct load (`lui t1; lw t1,%lo(t1)`), a direct store (`lui at; sw`), and the last block outside the counter's range. What we measured:

- A volatile access through `&D_800E6280` in the last block takes the block out of the range (regdiff: 0 defs). It costs one address instruction. `*(volatile s32 *)&G = G + 1` gets the load and the sum right, but the store becomes `lui t3; addiu t3; sw t2,0x1104(t3)` (7 lines). `G = *(volatile s32 *)&G + 1` gets the store right, but the load goes through `addiu` and every temporary shifts by one (7 lines).
- uopt folds a pointer local (`p = &G; *p`), a constant-propagated index (`((s32 *)&D_800E6280.unk_1100)[k]`), `*(u32 *)&G`, `*(u8 **)&G` and `.u` back into the same variable (242 lines). A dead `if (0)` volatile access is removed before allocation (242).
- A constant address is not taken to alias the counter, so a store through `*(s32 *)0x800E7384` (volatile or not) leaves the direct read in the range (242). A volatile absolute read changes nothing (6 lines). Reading at the top through the absolute address moves the chain from `$v0` to `$s0` (132). A redundant `G = t;` after the chain removes the counter's chain range (198).
- With two different constants (a read through `0x800E7384`, a store through `((GameState *)0x800E6280)->unk_1104.w`), nothing shares a register. But a constant address is a hoisted temporary, so the load is `lw t2,(t1)` with no reuse and the store base is `lui t4`, not `at` (12 lines).
- A block-scope `extern volatile GameState D_800E6280;` is a cfe error (different qualifiers). autotweak 120 s: 70 to 70.

Conclusion: plain C reaches the original only through a separate symbol for the last `+= 1`. That is also evidence that the original object used a separate view, but this evidence is a uopt live range, not the as1 hoisted pair that `migrate_globals` accepts. Follow-up (outside this package): decide whether a `keep` line may cite a live-range proof like this one. `func_80146754` has the same shape.

  - struct-field chains (`D.unk_038 = D.unk_036 = D.unk_037 = 0xA0`, any order) and separate statements give the right frame but three `li t6..t8`;
  - the element chain `(&D_800E6280.unk_036)[0] = (&D_800E6280.unk_036)[1] = (&D_800E6280.unk_036)[2] = 0xA0;` shares the `li` in `$v0` and stores in the original's order (037, 036, 038), but cfe adds a hidden 4-byte chain temporary below the locals.   - the hidden temporary is there in all 72 sharing forms tried (struct or element, any order, `GameState *g`, absolute address, separate `u8` externs); it is absent in all non-sharing forms. - **Frame model used** (OLH functions with ten saved registers, frame pass included): the lowest local sits at `base0 = 0x74`; locals take words top-down in declaration order, an array below the scalars declared before it; a chain's hidden temporary is the lowest word; F is `base0 + hidden + locals` rounded up to 8. So `i, r, col` plus 64 bytes of arrays give F = 0xC0 and `d` at 0x74; the same without `col` and with a hidden temporary gives F = 0xC0 and `d` at 0x78.
- **Method.** A scratch file under `build/scratch/` with many copies of the function, compiled with `python3 tools/cc.py <file> <out.o> ido 5.3` and read with `mips-linux-gnu-objdump -d` (grep `addiu sp,sp,-`, the array `addiu s5,sp,` and the `sb` lines), shows frame, array offsets and store registers for 12 to 72 variants per 30-second run. Faster than ninja plus funcdiff per variant.
- `func_80132114` is declared `void func_80132114(void);` in `include/ovl/OLH.h` (it had no prototype; the caller's implicit `int` declaration clashed with the definition) and `D_80139EE0` is declared there as `s32` next to `D_8013A700`.
