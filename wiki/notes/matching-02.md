## Wave 4, list 7 (T-6070): 24 functions, 5,520 bytes of the list's 127 functions (38,952 bytes)
Ticket [[tickets/T-6070-wave-4-list-7]]. The list held the leftovers of waves 2 and 3, so the yield is low (see the end). Patterns that worked:
- **Statements on one source line are scheduled as a unit.** `r.w = 0x20; r.h = 0x80;` on one line gives the original's `li w; li h; sh h; sh w` order, the same two statements on two lines give `sh w; sh h` (TT `func_80142DA8`, with `RECT r` and `func_8009C884(&r, arg0)`). The permuter found it (`do { ... } while (0)` on one line has the same effect). It is formatting, not C semantics, so the line carries a `FAKE` comment. The same `RECT` setup in TT `func_80142D40` matches this way, its 64-iteration loop is unrolled by IDO and not by the original (below).
- **`for (i = 0, p = base; ...)` allocates the registers in another order than `p = base; for (i = 0; ...)`.** TT `func_80144CA8` (`q = D_80158A6C; for (i = 0, p = D_80158AA4 + 0x64; i < (u32)(2 - q[0xC]); i++) { *p = 0; p -= 0x64; }`): the loop shape (the `beq` guard on `q[0xC] != 2`, `lbu` of `q[0xC]` inside the loop) is the for-loop with an unsigned bound; init in the header puts the counter in `$v1` and the pointer in `$a0` as in the original. TAIIKU `func_801448D4` moved from 24 to 3 differing words by the same change.
- **Implicit-int functions without a trailing `return`** (the `or v0,v1,zero` in the first delay slot of a switch chain): `s32 f(void) { switch (...) { ... break; } }`, `return;` turned into `break;` (TACO `func_80137BD8`, OPTION `func_8013AC30`). The other form: a function that ends in a call whose result the original returns without a copy: main `func_8004500C` calls `func_80044750` as the last statement of both branches and has no `return` after the stores; an explicit `var = func(); ... return var;` costs two `move`s.

Not the same as OPTION `func_80132624` (same arrays of 16 with a branch per element: IDO unrolls, the original does not).

## K&R promotion rules (T-7000)
Ticket [[tickets/T-7000-shared-constants-lui-at-parameter-copies]]. The brief was three wave-4 blockers: (a) a constant reused from a register across stores against one `li` per store, (b) one `lui $at` shared by neighbouring stores, (c) a narrow parameter copied at entry (`andi t6,a0,0xff; or a0,t6,zero`) or kept in its home slot. Method as in T-5010: scratch scans over every function of the main exe and the 26 overlays (matched and not), IDO's ucode compared pass by pass, full rebuilds compared per function with the baseline, and a sweep of m2c drafts (1341 asm functions up to 0x140 bytes) built with the new and the old toolchain.

### Finding: the original promotes unsigned char/short to unsigned int (K&R)
A value loaded by `lbu`/`lhu` is used unsigned by the original almost everywhere (first consumer within five instructions, all 6958 functions):
| consumer of an `lbu`/`lhu` value | unsigned | signed |
|---|---|---|
| compare with a constant | `sltiu` 1459 | `slti` 3 |
| compare with a register | `sltu` 104 | `slt` 6 |
| right shift | `srl` 556 | `sra` 0 |
| division | `divu` 101 | `div` 4 |
IDO in ANSI mode gives the signed form for plain C (`u8 < 10` is `slti`, `u8 >> 2` is `sra`, `u8 % 0x30` is `div`); that is why the matched C carried `(u32)` casts and `U` suffixes. IDO's K&R mode (`cc -cckr`, cfe `-std0`) gives the unsigned form for plain C: unsigned char and unsigned short promote to unsigned int. The few signed cases fit C that converts to int first (TT `func_8013AA44`'s `div` is an `s32` index).

The K&R front end also converts a narrow parameter in place at entry when it is passed on to a callee without prototype: `andi t6,a0,0xff; move a0,t6` (pattern (c), 12 functions in the original). IDO's ANSI mode gives this only for a `u8`-prototyped callee.

One part of IDO's K&R ucode is not the original's: IDO drops the widening `CVT` of an unsigned narrow load, and uopt's operand order and register promotion depend on it. In the original a compare of a narrow global with a constant held in a register has the constant first (`lbu` 310 against 76, `lh` 40 against 8: uopt swaps when the left operand is not a plain variable), a word global has the variable first (`lw` 83 against 24), and a narrow local read from its stack slot has the variable first (55 against 0; parameters 7 against 0). So the original kept the widening for globals only. `tools/cvt_pass.py` now puts IDO's ANSI `CVT J<-L` back after a load of a narrow unsigned global (not before a store, conversion, array index, `++`/`--`, truth test, operand swap or narrow parameter, where ANSI writes none either; a switch temporary gets one), and its T-1321/T-5010 rules then work as before. Checked by comparing cfe's ANSI ucode with the widened K&R ucode over all 440 C files: of 1711 narrow global loads, 28 differ (24 compares and shifts written with an explicit unsigned operand, 4 operand swaps). Widening locals as well was tried: it fixes one matched function and breaks another, and the stack-slot statistic above says no.

Build: `-cckr` in `tools/cc.py` `IDO_CFLAGS` plus the widening step. With `-cckr` and the old pass, 29 of the 3507 C functions in the build changed; the widening brought most of them back. The rest were C written for ANSI promotion, and 14 functions were adjusted (all in the first T-7000 commit): `U` suffixes and `(u32)` casts dropped (DATE `func_8013D3B0`, `func_8013E614`, EVENT `func_8011A508`, main `func_800847B8`), an `s32` index or intermediate for a signed `div` (TT `func_8013AA44`, `func_8013AACC`, `get_h_yuukou`), `(s32)` for a signed subtraction (`func_80057640`), a `u32` copy (KANGEI `func_80134EA8`), a `u32` return (SHUGAKU `func_80135B68`), `for (i = 0, n = 10; ...)` (EN_NICHI `func_80133924`), `D_8015EB9C` declared `s32` (RPG_BAT `func_8013BEA8`), `s32 func_8009AD70();` (TACO `func_8014A8E0`), and GYOZI `func_80135D64` keeps its `FAKE` with the local copy the permuter found. Clean build 27/27 OK, no other C function changed.

### Verdicts
- **(c) Parameter copies: source (K&R), solved.** The copy-back at entry is the K&R front end's code for a narrow parameter passed on to a callee that has no prototype. Write the parameter with its narrow type and declare the callee K&R (`void f();`); a prototype on the callee gives IDO's `andi a1,a0,0xff` near the call instead. Matched: ETC `func_80132048` (with `void func_80042878();`), TACO `func_80136E70` (`void func_80139424();`), TT `func_8013C764`, main `func_8007B5EC`, `SD_DetectCDPeak`, `set_kanji_string` (its `s16` first parameter stays in its home slot and is read with `lh` after the call). Related: RPG_BAT `func_8014F1D4` calls `func_8014EF6C` with and without an argument, which needs the callee defined without prototype. Not matched: `SD_CalcCDAve` (two loop temporaries swapped), `func_80045318`, `func_80045414` (the original keeps the clamped parameter in its home slot and reloads it around the calls, IDO puts it in `$s0`), TT `func_80148C94` (the buffer sits 12 bytes lower in the frame), `func_8013230C`, `func_80147A18`. A modified parameter read back from its home slot (TT `func_80148B6C`, `func_80049FF0`) is IDO's spill choice, not K&R.
- **(a) Constants shared across stores: mostly source, partly open.** Three mechanisms:
  - Constant types: uopt keeps one register for a constant only between uses of the same type, and under K&R a constant that meets an unsigned operand is unsigned. So `u8 == 1` and `s32 == 1` load `li at,1` each, as in the original. The EVENT/DATE compare chains that needed `(u32)` casts or `1U` match as plain C: EVENT `func_8011A2C4`, `func_8011A4A4`, `func_80119600`, `func_80118764`, `func_80116360`, DATE `func_8013E5B0`, `func_8013BDB4`, TACO `func_8014EDCC`. DATE `func_8013A344` comes within 2 instructions (an `s32` global compared with a shared 3, constant first in the original).
  - Chain assignment to aggregate elements: IDO keeps the value in one register (`$v0`, `$v1`) for `a[i].x = a[j].x = k;` when the targets are array or record elements (the stored value is forwarded), and re-loads the constant for scalars and plain struct members (`A = B = k`, `S.a = S.b = k`), as for separate statements. EVENT `func_80102C0C` (`li v0,8; sb v0,A; sb v0,B` on two 0x44-byte records) matches with `D_800EAFA0[4] = D_800EAFA0[0x48] = 8;`. The RGB triples of `D_801217D0[k].unk_14..16` (`li v0,0x80`; `normal_date_girl_suddenin`, DATE `func_8013FA6C`, EVENT `func_8011B5A8` and others: 118 unmatched functions store one constant from a `$v`/`$a` register twice) have this shape; the two tried come within 2 instructions (an extra `or v0,v1,zero` copy, or the `li`/`lui` order) and stay asm.
  - Constants in ugen temporaries (`li t6,3; sh t6,A; sh t6,B`, the third store later; DATE `func_8013DCC0`, EVENT `func_80119C9C`, TT `func_80136C64`, `parameter_show_init`: 41 functions): open. IDO's ugen reuses a temporary only when the next register of its rotation still holds the constant (matched `func_800418B0`); the original reuses one out of rotation. The stores come in chain order per record (b, a, later c), so these are probably chain assignments too, with the chain value kept in an ugen temporary; no IDO form found.
- **(b) Shared `lui $at`: toolchain plus data ownership, no pass.** Re-measured over the original: `lui $at` is shared between two different addresses with the same `%hi` in 255 places and re-emitted in 16233. 231 of the shared pairs are overlay data, 24 main data, and each main group is data that only the sharing file uses (`D_800B3F60`: 8004E500 only; `D_800B3D70`: 800451D0; `D_800B6990`: 80075320; `D_800CA2A4`: 8007C030; `D_800B5920..`: shared by `dec_bg_reset` in 80057390, re-emitted by DATE). `GameState` fields, which every unit uses, are never shared. With the recovered types the C reaches neighbours through one base symbol in 221 matched functions (758 places, up from 135 functions in T-5020) where the original re-emits, so a symbol-keyed as1 rule alone is wrong. The data fit this rule: the original's as1 shared `$at` for data defined in the same source file (reached through that file's own section symbol), and every other access named its own symbol. The build cannot do this until data is defined per object ([[tickets/T-3052-per-object-data-bss-split]]); an as1 pass keyed on the object that owns the data would then be uniform. The 74 functions stay asm.

## Game-state views audit (T-7010)

## Loop unrolling and scheduling (T-7020)
Ticket [[tickets/T-7020-loop-unrolling-and-scheduling]]. Wave 4 listed two blockers: (a) IDO unrolls loops the original does not, (b) IDO places loads, delay slots and shared constants differently. Verdict: both come from the C, not from the compiler. IDO 5.3 makes the same unroll decisions as the original, and its assembler schedules by the same rules. No option and no pass was adopted; `tools/cc.py` and the flags are unchanged.

### Method
- Corpus scan (scratch scripts, not committed): every function file of the main exe and the 26 overlays (SDK excluded), 1419 functions with a backward branch, each loop classified by unroll factor (offset groups against the induction step), test (`bne`, `slti`, `sltu`), remainder prologue, calls, and the order of the loads in unrolled copies. Matched functions (298 with loops) are the controls: for them IDO and the original agree by definition.
- IDO probes: scratch C compiled with the build's pipeline (`cc.py` + `cvt_pass` + `frame_pass`), with `-Wo,-unrolllimit,N` binary-searched per function to read uopt's per-copy cost, and with an `as1` shim that rewrites binasm records (`.loc`, `-O`).
- Each rule below was then tested on blocked functions; a rule counts as proven when functions match because of it.

### When a loop is unrolled (rules of IDO 5.3, which the original follows)
1. **Budget.** uopt gives each loop body a cost C and unrolls by 4 when 4C fits the limit, by 2 when 2C fits, else not; the default limit is between 264 and 341 (a 66-unit body unrolls by 4, a 171-unit body does not unroll). A body of n stores through a struct-array index costs about 3n up to 18 stores and about 9n from 19 stores on (main `func_800415B4`: 19 stores, 171, not unrolled; `func_8004164C`: 17 stores, 52, unrolled by 4 with a run-time remainder; both as in the original). OPTION `func_80132624` (16 elements, a branch per element) is unrolled by 2 by the original and by IDO alike; T-5020 read it as not unrolled.
2. **Trip count.** Constant counts: 2 or 3 trips stay a rolled loop; 4 to 7 trips are unrolled completely (straight-line code, no branch); 8 and more become an unrolled-by-4 loop with the N mod 4 left-over copies first. Count the trips from the end address (ETC `func_80140DC8` is 83 trips: 3 copies, then 20 rounds of 4). TT `func_80142D40` is a 256-trip loop over 0x20-byte steps (`for (i = 0; i < 0x2000; i += 0x20)`), not a 64-trip loop with 4 stores; it is unrolled by both compilers.
3. **Counter assigned again later: rolled.** A counted loop stays rolled (one copy, `slti`/`bne` on the counter) when its counter variable is assigned again after the loop: the same `i` in a later loop, `i = f();`, or `i = 1; return i;` (TT `func_80132B88`: first of two loops over `i`). The init has to be right before the loop; `i = 0;` before an enclosing `if` does not count. Evidence: of the 70 rolled `slti` loops without a sign extension in unmatched functions, 58 are followed by another loop in the same function, against 105 of 267 unrolled-by-4 loops.
4. **Loops without a conditional back edge are never unrolled** (`for (;;) { ...; if (++i == n) break; }`, a `goto` loop). Narrow counters (`s8`, `s16`, `u8`) are never unrolled either; they show as `sll/sra` or `andi` on the counter.
5. **Nested loops.** An inner constant loop of 4 is unrolled completely and the outer loop stays rolled with the end address in a register (main `func_800673B8`: `for (i = 0; i < 32; i++) {` / `for (j = 0; j < 4; j++) D_800E6280.unk_163C[i * 4 + j] = 0;` / `}`). T-5020 found no C for this "hoisted end pointer with a constant trip count".
6. **Pointer loops.** `p < end` is never unrolled (`sltu`). `p != start + N` (same symbol) is not unrolled. `p != &OTHER` gets a run-time remainder (`subu; andi 0x3F`), which no original function has: the original's pointer-compare loops are index loops that uopt strength-reduced. Write the index loop (`D_8011ECD0[0x443 + i * 0x44]`, `D_8013984C + i * 0x30`).

### Scheduling (rules of IDO 5.3's as1, which the original follows)
1. **Source lines.** as1's scheduler uses the `.loc` line records. Proof that the original's assembler did the same: a full build with every `.loc` removed from the binasm changes 906 of the matched functions. Consequence for unrolled loops: with the body on the line of its `for`, IDO loads copy 0 first (`lbu 0x443; lbu 0x487; ...`); with the body on its own line it loads copy 0 last. In the original, 73 straight-line unrolled loops load copy 0 first and 34 last; matched: hizuke_disp_switch, parameter_disp_switch, OPTION `func_80134210`, `func_801385F0`, `func_80137FA0`, TACO `func_80133410` with one-line loops.
2. **Fully unrolled loops explain "load hoisting" and `lui` placement.** A run of read-modify-writes on fields one record apart, each `lh` after the previous `sh`, with the next `lui` above the previous store, is a 4-7 trip loop that IDO unrolls completely (TAIIKU `func_80140338`: `for (i = 0; i < 4; i++) *(s16 *)&D_8011ECD0[0x1AA8 + i * 0x44] -= 4 - i;`; `func_8014038C`, `func_801450C0`: `+= t.v[i]` from a local copy of a 4-entry table; `func_80148820`, `func_80148678`, `func_80145044`, `func_801487B4`). Written as separate statements on separate symbols, IDO's as1 moves the loads up (T-6010, T-6070).
3. **One base symbol keeps the loads in place.** as1 moves a load above a store only when the two have different symbols; neighbours read after a store go through one base symbol (`*(s16 *)&D_8011ECD0[0x1998]`, `D_801206D8[0x1037]`), as CODING_STANDARDS 8 says for aggregates.
4. **Delay slots and init order.** In TT `func_80132C24` the original fills the `bne` delay slot with the counter init (`move v1,zero`); IDO does that when the counter is initialised before the pointer (`i = 0; q = D_80158AA8; for (; ...)`), the order that also gives the original's pointer/counter registers (TT `func_80146BE0`, `func_80146C14`).
5. **Shared constants by type.** `p[0x1D] == 0x80U` keeps the compare's `li at,128` apart from the loop bound's `li a1,128`; `== 0x80` shares one register (T-6050 note on constants of different types).

### Options and passes tested (none adopted)
- `-Wo,-unrolllimit,N`, `-Wo,-nomultibbunroll`: the T-5020 rebuilds stand (changes to matched functions below N = 200); the blocked loops did not need them once the C was right.
- as1 `-O0/-O1/-O3`: the binasm `.option O 2` record overrides them ("Binasm file dictates -O: 2"); with the record rewritten nothing changes the load order.
- Dropping or flattening `.loc` records before as1: fixes the copy-0 order of one-line-less loops but changes 906 matched functions (rule 1 of Scheduling), so the original was line-sensitive.
- uopt `-zdbug` is not usable in the recompiled uopt (T-3100); the cost model above was read with `-unrolllimit` instead.

## Shared `lui $at`: data defined in the file (T-9010)

Correction of (b) in "Shared constants, shared `lui $at` and loop unrolling" (T-5020) and of the T-7000 note: **IDO 5.3 does share `$at`**, by itself, between stores to different offsets of one symbol when that symbol is defined in the same file. Measured with `cc -O2 -Wo,-nokpicopt -cckr` on scratch files: `short arr[4] = {...}` (initialised global), `static short sarr[4]`, a struct `S st = {...}`, and an uninitialised `static int y[4]` (`.lcomm`) all give one `lui $at` for `arr[0..3] = ...`; an `extern`, a tentative definition `int x[4];` (common in K&R mode) and two different variables (`a1`, `a2`, or two statics `s1`, `s3` of one section) re-emit `lui $at` per store. The T-5020 measurement had used externs and scalar statics. This is exactly the original's rule (T-7000: shared groups are data only the sharing file uses; `GameState` fields, reached from every unit, are never shared; no conflict inside one object), so no as1 pass is needed: the C file that owns the data has to define it ([[decompile-workflow]], "Data defined in the C file").

Other measured facts that the data tools rely on:
- IDO emits a file's `.data` in source order and starts every data definition on a multiple of 4 (`char a[1]` at 0, `char b[5]` at 4, `char c[3]` at 0xC); the section is aligned and padded to 16. An unaligned splat symbol in the original data is therefore a member of the variable before it.
- A member of a defined struct compiles like a scalar for a switch selector (`switch (D_8015EDB0.unk_00)`: `lw v0`), an array element does not (`switch (D_8015EDB0[0])`: `lw v1`, 5 matched RPG_BAT functions changed). Use a struct when other code switches on the members.
- Defining the data does not change the T-5010 selector rule: an entry switch on a defined `u8` still gets `$v1` from `tools/cvt_pass.py` (without the pass, IDO gives `$v0` for both). A scan of the original's entry selectors (`lbu`/`lhu` into `$v0`/`$v1` before the first branch or call, then a compare) against the T-9010 data ranges: data in the function's own object 22 `$v0` to 2 `$v1`; data of another object 132 to 265; objects without a range 126 to 31. So the `$v0` cases that cvt_pass gets wrong are mostly unit-private data, as the U0 note in `tools/queue.py` says. A cvt_pass rule that leaves variables defined in the file alone is a candidate (not made here; cvt_pass is not in this ticket).

- **Selector copy `or v0,v1,zero`.** Source: an `int` function without a return value (above). Where the selector is loaded after a call or branch and the original still has `$v1` (U1), nothing in IDO's input changes the allocation (T-5010). No pass.
- **Unsigned narrow global kept across blocks** (including the `andi` cluster). Property: uopt's register-promotion priority (the benefit of a live range against its save cost), not visible in the ucode. Evidence that no ucode-local rule separates it: of the narrow unsigned globals that a function loads before its first branch and also stores, the original keeps 81 in a register and leaves 80 in temporaries among the matched functions alone (IDO already reproduces both); the sharpest case is one variable: main `bustup_wink` (matched) and ENDING `func_80137574` are both `if (!(D_8011F4CA & 1)) D_8011F4CA |= k` (k = 0x11 and 3); the original gives `ori t8,v0,0x11; sb t8` in the first and `ori t7,v0,3; andi v0,t7,0xff; sb v0` in the second.
