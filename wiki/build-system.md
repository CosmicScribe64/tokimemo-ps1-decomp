# Build system

`build/SLPM_86.053.bin` builds byte-identically to the original executable (SHA-1 `e823bd844a8f8fa4d05483b59c66bc54b8393b26`). At the initial milestone, the game functions lived in the 28 files `src/main/<address>.c` (834 functions, 75 in C, the rest `INCLUDE_ASM`; see [[source-files]]), with the SDK/lib region (65 asm segments; see [[psyq-sdk]]) and data as plain assembly.

## Commands (all through Docker)

`tools/docker.sh` builds and runs the image natively for the Docker host (`arm64` on Apple Silicon, `amd64` elsewhere). Setting `TOKIMEMO_PLATFORM=linux/amd64` forces the emulated `amd64` image, which is the only one carrying all old-gcc compilers. Both images produce identical binaries; see [[toolchain]] ("Native image", T-3310). A clean build takes about a third of the time natively on Apple Silicon.

1. Put your copy of the game in `game/` (gitignored; BIN+CUE, CHD, ISO, or a `.zip`/`.7z` of those at any depth; see `game/README.md`). No manual extraction is needed because `configure.py` adds the Ninja step `build/disc.stamp` (rule `disc`, `tools/prepare_disc.py`, T-3300). It finds the image(s) in `game/`, identifies the release with `tools/identify_version.py`, and unpacks the one whose executable matches the SHA-1 of `config/SLPM_86.053.sha1` into `disc/files/` (`tools/extract_disc.py`, supporting raw 2352-byte or cooked 2048-byte sectors since the build needs only the files). Other releases (`rev1`, `rev2`, `rev4`, `shokai`) fail with a message naming what was found, and missing images with no `disc/files/SLPM_86.053` fail with a message pointing to `game/`. An already-populated `disc/` (in CI or via `extract_disc.py` by hand) is enough if `game/` is empty. The step reruns only when an image in `game/`, one of the tools, or `config/versions.txt` changes, and a new file in `game/` regenerates `build.ninja` (the directories are inputs of the generator). The splits depend on the stamp rather than on `disc/files/*`. The repo-root zip is no longer searched.
2. Run `tools/docker.sh python3 configure.py` to write `build.ninja` (Ninja regenerates it when `configure.py` changes) and `objdiff.json`.
3. Run `tools/docker.sh ninja` to split, assemble, compile, link, and check the SHA-1 of the main executable and all 26 overlays (the default target). `ninja overlays` builds only the overlays, and `ninja build/ovl/TT.ok` builds one overlay.

T-9400 adds `build/symbols.ok` beside the header and global checks. `tools/check_symbols.py` rejects any active assignment at or above `0x80132000` in `config/symbol_addrs.txt`. Put overlay symbols in `config/symbols_<OVL>.txt`, referenced from that overlay's YAML. C compilation and the default build depend on the guard, and changing the shared symbol file invalidates its stamp.

T-27002 widens the check to the symbol files of every YAML (`tools/symtab.py`). It enforces one name per address and one address per name in each unit, and forbids main names inside EVENT's range (`0x800F6000`–`0x80126000`) in any file EVENT loads (`cd_read_status` moved to `config/symbol_addrs_main.txt`). It also enforces one name per main address across units and rejects names that differ only in case. A line whose comment holds `alias-view` is a deliberate second name (`func_80084C98`). The stamp is written only when missing and the rule uses `restat`, so a symbol file edit does not rebuild every C object.

`build/main_names.ld` takes every main-YAML symbol file that the overlay YAMLs do not load, plus `config/symbol_addrs_types.txt`. Since T-27003, the overlay YAMLs also load `config/symbol_addrs_obin.txt` and `config/symbol_addrs_sdk.txt` (listed in the generator template), so those two files are no longer inputs of `main_names.ld`. Each overlay link gets the names from its own `build/ovl/<NAME>_undefined_funcs_auto.txt`. Each overlay split prints splat's "Unable to determine a segment" list for names outside the overlay (about 540 more lines each, or 1.2 MB for a clean build). Address `0x80084C98` produces a single splat warning (`sprite_brightness` overlaps `func_80084C98`) for the deliberate two-name address. `build/renames.ok` (`tools/rename.py check`, default target) keeps renamed symbols from returning; see [[rename-tool]].

## Progress and per-function diff

- `tools/docker.sh ninja progress` (or `tools/docker.sh python3 tools/progress.py`, tests in `tools/test_progress.py`, T-0602) prints decompiled versus total functions and bytes, counting functions still using `INCLUDE_ASM` against sizes from the splat `nonmatching` headers. The report includes one row per `src/main` file against `asm/{nonmatchings,matchings}/main/<addr>/` with a `main game` subtotal (834 functions, 284,428 bytes). Next comes one row per overlay across all its C files (`src/ovl/<NAME>.c` or per-object `src/ovl/<NAME>/<addr>.c`, each against `asm/ovl/<NAME>/{nonmatchings,matchings}/<name>/`, with the file list read from the YAML files through `tools/srcscan.py`, T-0500). That section ends with an `overlays` subtotal (6,128 functions, 1,994,940 bytes; the overlay configs set `disassemble_all` so decompiled functions keep their size). It then prints a `grand total` (main + overlays, 6,962 functions, 2,279,368 bytes) and a separate `SDK libs` line (722 functions, 165,212 bytes from top-level `asm/*.s`) that stays asm-only and is not counted in any denominator. At the T-1310 snapshot, counts were main 268/834, overlays 458/6,128, and grand 726/6,962.
- `tools/docker.sh python3 tools/funcdiff.py <func...>` finds the `src/main` file that holds each function and diffs it against the original object `expected/<built path>` (`expected/build/src/main/<addr>.o`). It builds the expected object from the original disassembly with `tools/cc.py` (an all-`INCLUDE_ASM` stub of the file with key file `expected/<path>.key`, rebuilt when an original `.s` changes, T-7030). See [[decompile-workflow]].
- `tools/docker.sh python3 tools/queue.py [--next N] [--files ...]` (T-1320, tests in `tools/test_queue.py`) prints the ranked work list with blocker flags for the main executable and all overlays ([[decompile-workflow]], [[matching-notes]]). `tools/list_leaves.py [--file ADDR]` is a wrapper that lists remaining main-executable leaf functions, and `tools/docker.sh python3 tools/game_boundaries.py` reprints the file-boundary evidence ([[source-files]]).

## Reusing C across identical functions (T-1300)

`tools/docker.sh python3 tools/dupes.py [--apply [--check]] [--unit NAME] [--lenient] [-v]` (tests in `tools/test_dupes.py`) requires a built `asm/`. It fingerprints every function in `asm/{nonmatchings,matchings}` across `main` and the 26 overlays by masking `%hi/%lo`, `jal`/`j` targets, and branch-to-symbol offsets in instruction words while keeping register and opcode bits. Initially, functions with jump tables or data were ignored.

For groups that have one function already in C and unmatched members, `dupes.py` copies the C, renames the function, and maps symbols by position in the relocation sequence (one-to-one with equal addends). It identifies main-executable symbols by address through `config/symbol_addrs*.txt`, so `func_8007ED84` and `bg_read_sub2` resolve to one symbol. Declarations of the target's symbols are copied from the source header closure into the target overlay header (created with the `#include` when the overlay has none) or `game.h`/`main_only.h` for `main`, unless the target already declares them identically. The tool skips ambiguous cases and lists them under `-v`, including string literals, `static`, unmapped calls, unknown types, or a differing target declaration. Passing `--lenient` accepts the target's own declaration and lets the build judge. `--apply --check` builds each touched object (`build/ovl/NAME.ok`, `build/SLPM_86.053.ok`), and on failure reverts it and retries copy by copy, keeping only the ones that match. Finish with a clean build as the final gate.

T-7030 diagnosed wave-4 failures (where 0 of 5 applied from 201 unmatched members, and `-v` now names the reason for every skip) and fixed seven causes, each with a test:

1. In about 75 members, the C names `D_800E6280.unk_110D` where the asm relocates `D_800E738D`, referencing a symbol absent from the relocation sequence. `migrate_globals` resolves the path to its address and keeps it when the target uses the same address. When the address differs, it rewrites the access to the target's field (`migrate_globals.find_mapping`) or plain global.
2. When `MAIN_API_OVERRIDE_<sym>` views of the source file (a `u32` selector) were not copied, causing the target to build the `s32` view of `main_api.h` (switch in `$v0` instead of `$v1`), the define and the declaration are copied into the target file.
3. File-local typedefs (`FnTbl25`) are copied with the body, and a declaration with a type defined only in `.c` files stays in the `.c`.
4. `*(s16 *)0x801F0D14` corresponds to `%lo(D_801F0D14)`, so the literal becomes the target's address.
5. The target's prototype wins. A header `void` that callers assumed learns the twin's return type, and an `s32` prototype keeps the definition `s32`. A target without a prototype gets one (where an earlier call made it implicit `int f()` and clashed with the definition), and a callee defined further down in the target file gets a prototype in its header.
6. `f()` and `f(void)` are treated as one view, and a difference in the return type alone is not a conflict.
7. Main-executable declarations are no longer appended to `main_api.h` by hand. The batch runs `sync_protos.py --fix` (handling guards and `MAIN_API_OVERRIDE_` for overlay data over the main `.bss`, such as EVENT at `0x801206B0`), and the whole `include/` tree is restored when a copy is rejected.

Remaining skipped cases include conflicting views of an overlay-private global (`s16` against `u16`, `s32` against `u8 *`, scalar against array) and constant-index elements of an array (`D_80120650[7]`, relocation `D_80120657`). They also include struct types defined in another overlay's header (`GyoziRec44`, `TaiikuBig`) and an element of the `GameState` struct array against a plain global (IDO orders the two forms' loads differently).

### Jump-table twins (T-11150)

Both tools now fingerprint functions with jump tables and local labels. A `j .L` target and a `%hi/%lo` of a `.L` label are masked and kept as the offset from the function start. A `jtbl_` relocation is masked and kept as the table's position. The table words (from the function file's `.late_rodata` written by `rodata_pieces.py`, or else from the unit's splat data files) join the fingerprint as offsets from the function start, requiring twins to have the same table. A table ends at the first word that is not a label (padding); an entry outside the function or a missing table excludes the function. Strings in the function file excluded it (`data in function`) until T-11160 below.

A plan for a jump-table target is classified as `island` when all its tables live in its own function file, where the C object provides its `.rodata` and the compiler's table takes the original's place. An `island` plan is applied only with `--apply --check`, whereas `outside` (no island, orphan chunk) is never applied. The summary prints `jump-table groups N (M unmatched members); fillable ...; needs jtbl check ...` along with one `NEEDS JTBL CHECK unit/func <- src: reason` line per plan. See [[tickets/T-11150-twin-detection-for-jump-table-functions]].

Functions with their own `.rodata` also participate (T-11160, previously skipped as `data in function`). Own `.rodata` is a symbol of the function's C object island (`<asm_path>/data/<name>.rodata.s`) or of the `.rodata` that `rodata_pieces.py` appended to its file. Its `%hi/%lo` is masked and kept as its position among the function's data symbols. Its directives (comments stripped, strings Shift-JIS escaped as `asm.py` does, `.word .L` as the offset from the function start, and `.word SYM` as a marker) join the fingerprint so twins must have equal data. The source C may then hold string literals (copied verbatim).

A plan's `data` classification is `island` (all own data in its function file, applied only with `--apply --check`), `outside`, or `pointers` (never applied). For these functions, the report outputs `data-in-function groups N (M unmatched members, B bytes); fillable ...; needs data check ...` and one `NEEDS DATA CHECK unit/func <- src: reason` line per plan. Non-instruction lines in the function text still exclude a function (`data in function text`), as do unknown `.rodata` directives (`unparsed rodata in function`). See [[tickets/T-11160-twin-detection-for-data-in-function-functions]].

### Near duplicates (T-3320)

`tools/docker.sh python3 tools/neardupes.py [--report | --apply [--check]] [--unit NAME] [--func NAME] [--lenient] [-v]` (tests in `tools/test_neardupes.py`; run after `dupes.py`) extends twin detection to functions with equal code shape and differing constants. The fingerprint also masks the 16-bit immediate of `addi/addiu/slti/sltiu/andi/ori/xori/lui` (except on `$sp`, keeping frame size and local addresses in the shape), while load/store offsets, shifts, and branch offsets stay so a group shares opcodes, registers, and relocation positions. A `lui` plus the `ori`/`addiu` completing it count as one 32-bit constant.

For an unmatched member without a byte-identical matched twin, `dupes.plan_copy` renames the function and maps symbols and declarations, and then substitutes each constant that differs between the matched member and the target by value in the C text. A substitution occurs only when it is unambiguous. Every instruction carrying the source value must map to the same target value, and the value must occur as a C literal. A leading or binary minus counts as its sign, and decimal or hex style and digit width are preserved. The literal must also appear no more often than there are instructions carrying it, preventing accidental changes to an array index or similar constant. Otherwise the function is skipped with a reason (`no C literal` for enums, macros, and folded expressions; `maps to different constants`; `N C literals for M instructions`; sign flip in a subtraction; plus the `dupes.py` reasons).

`--report` (the default) prints groups, fillable members and bytes, skip reasons, and groups with no matched member (match one and `--apply` fills the rest). It also reports functions not fingerprinted (jump tables, string data) and how many more a load/store-offset-masked shape would cover. `--apply --check` writes the C and builds each object like `dupes.py`. Limits include a differing relocation addend, `x > N` compiled as `slti N+1` (where the literal differs by one from the instruction), constants from `sizeof` or enums, and the 1,400+ unmatched jump-table and string functions that `dupes.py` originally excluded.

## Pipeline

The main build pipeline runs in five stages:

1. `splat split config/SLPM_86.053.yaml` generates `asm/` (gitignored) and `build/SLPM_86.053.ld`. Each `c` subsegment of the `main` segment corresponds to a `src/main/<addr>.c` file that splat creates only if missing (with `INCLUDE_ASM` per function, edited afterwards and never regenerated).
2. Assembly objects compile via `mips-linux-gnu-as`. C files compile via `tools/cc.py` with the toolchain `configure.py` assigns per file (`C_FILES` is read from the YAML's `c` subsegments, using IDO 5.3 unless listed in `C_TOOLCHAIN_OVERRIDES`). IDO 5.3 runs through `asm-processor` with the frame-layout emulation pass `tools/frame_pass.py` (see [[toolchain]]), while the GCC path (`cpp | cc1 | maspsx | as`) is kept for SDK C. Stage failures abort the build, and the depfile lists the `INCLUDE_ASM` `.s` files.
3. `ld -T build/SLPM_86.053.ld -T build/undefined_syms_auto.txt` links the ELF.
4. `objcopy -O binary` extracts the binary (the header section is the first `0x800` bytes, producing the complete PS-X EXE).
5. `sha1sum -c` verifies the output against `config/SLPM_86.053.sha1`.

## Frame pass

Every IDO compile (main executable and overlays) goes through `tools/frame_pass.py` via an `as1` shim under `USR_LIB` (details in [[toolchain]]). `configure.py` lists `tools/frame_pass.py` as an implicit input of the C compile rules, so changing it rebuilds all C. `tools/docker.sh python3 tools/test_frame_pass.py` runs its unit tests.

## Overlays

Each overlay in `config/overlays.txt` is its own target (see [[overlays]]):

1. `splat split config/overlays/<NAME>.yaml` generates `asm/ovl/<NAME>/` (gitignored) and `build/ovl/<NAME>.ld`.
2. `tools/cc.py` builds one IDO object per `c` subsegment (`src/ovl/<NAME>.c`, or `src/ovl/<NAME>/<addr>.c` per original object after the T-0500 migration; see "Per-object C files" below) alongside the `.rodata`/`.data` assembly objects.
3. `ld` links the objects with the splat script and `build/ovl/<NAME>_undefined_{funcs,syms}_auto.txt`.
4. `objcopy -O binary` extracts the overlay binary.
5. `sha1sum` checks the output against `config/overlays/<NAME>.sha1`, writing `build/ovl/<NAME>.ok`.

Splat created the 26 `src/ovl/*.c` files once (with every function initially `INCLUDE_ASM`), and they are committed and never regenerated. `config/overlays/*.yaml`, the SHA-1 files, and `config/overlays.txt` come from `tools/docker.sh python3 tools/gen_overlay_configs.py` (requires `disc/`). All 26 overlays rebuild byte-identically; `O.BIN` is not built ([[tickets/T-0201-obin-format-and-symbols]]).

## Gotchas found

- `gas` pads the standard `.text` section of every object to 16 bytes, shifting everything after a library object whose size is not a multiple of 16. `tools/asm.py` assembles splat's `.section .text` into the custom section `.text.sdk` (no padding) and renames it to `.text`. The linker script's `SUBALIGN(2)` then keeps placement exact (T-0010).
- `configure.py` derives `ASM_FILES` from the `asm` / `rodata` / `data` / `bss` subsegments of `config/SLPM_86.053.yaml`, so splitting a segment requires no `configure.py` edit.
- Splat rewrites `include/include_asm.h`, `macro.inc`, and the other `.inc` macro files on every split, clobbering the hand-edited IDO guard from T-0013 and breaking the IDO build after the first split. Both the main config and all overlay configs set `generate_asm_macros_files: False` to prevent that.
- `asm-processor` rejects a function that is a single 4-byte `nop` ("too short .text block"), which caused the 1-nop pad problem solved by the trailing padding pass of T-1310 (see [[toolchain]]).
- The linker aligns each section end to 16 bytes, so the overlay code segment must end on a 16-byte boundary (the generator rounds up) or later symbols shift.
- IDO cannot parse `__asm__`, so `include/include_asm.h` skips its macros when `__sgi` is defined. `asm-processor` replaces the `INCLUDE_ASM` lines and assembles them with GNU `as` and `include/asmproc_prelude.inc` (label macros without `.ent`/`.end`, plus `gte_macros.inc`). It runs with `--convert-statics no` because its `.mdebug` static-symbol import crashes on IDO `-EL` objects; C `static` symbols are therefore not visible to `INCLUDE_ASM` code.
- `ld_gp_expression` must be a string, and `include_macro_inc` is not a splat 0.50 option.
- Setting `string_encoding` and `data_string_encoding: SHIFT-JIS` (T-0012) makes splat write readable UTF-8 `.asciz "..."` lines with the raw hex in a comment. Because `gas` would otherwise emit UTF-8 bytes (`+0xC70` total in the main executable), `tools/asm.py` re-encodes every non-ASCII character of a `.asciz`/`.ascii`/`.string` literal to Shift-JIS octal escapes before assembling, keeping the bytes exact. Both the main config and all overlay configs (via `tools/gen_overlay_configs.py`) use `SHIFT-JIS`; run `tools/docker.sh python3 tools/test_asm.py` from `tools/` for tests.
- Linking the main executable requires `build/undefined_syms_auto.txt` (131 addresses in overlay and heap space; see [[overlays]]).
- Splat emitted four tiny functions (`func_80066A68`, `func_80066A70`, `func_80066A78`, `func_80066AC0`) with `jlabel`, producing harmless `.end without .ent` assembler warnings.
- In a fresh checkout before `generate_asm_macros_files: False` was set, the first `splat split` rewrote the committed `include/include_asm.h` with splat's own version (lacking the `__sgi` guard), causing the IDO compile to fail with `cfe: Error: include/include_asm.h, line 27: Syntax Error`. Restore it with `git checkout include/include_asm.h` and rerun `ninja` (T-0014; tracked in [[tickets/T-0101-splat-overwrites-include-asm-h]]).
- Generated `asm/` contains game code and must never be committed (gitignored alongside `build/` and `disc/`).

## objdiff

`objdiff.json` (written by `configure.py`) has one unit per `src/main` file (target `expected/build/src/main/<addr>.o`, base `build/src/main/<addr>.o`) and one per overlay (target `expected/ovl/<NAME>.o`, base `build/ovl/<NAME>/src/ovl/<NAME>.o`). Copy the all-`INCLUDE_ASM` objects to `expected/` once for per-function diffs; `expected/` is gitignored. Units carry the progress categories `main` and `overlays`. CI builds its own target and base objects from the full build with `tools/report_objs.py`; see [[ci]].

See [[ci]] (T-0902) for CI, the encrypted game bundle, and the decomp.dev report; [[executable]] for layout facts; and [[toolchain]] for the compiler pipeline.

SDK names (T-0010) live in `config/symbol_addrs_sdk.txt` and provisional `O.BIN` game names (T-0600, [[obin]]) live in `config/symbol_addrs_obin.txt`. Initially only the main config read both files (both are `split` inputs in `configure.py`), whereas the overlay configs also loaded the shared `config/symbol_addrs.txt`, where splat warns on symbols outside the overlay segment.

## Per-file layout notes (T-0012)

- To add or move a file boundary, edit the `c` subsegment list in `config/SLPM_86.053.yaml` (names `main/<vram>`, start = file offset) and move the functions between `src/main/*.c`; `configure.py`, `objdiff.json`, and `progress.py` follow automatically. `INCLUDE_ASM` folder names are `asm/nonmatchings/main/<addr>`.
- `tools/trailing_pad.py` (T-1310) re-inserts the original's trailing `nop` words after every C function, read from the function's splat `.s` ([[toolchain]]); no `src/ovl/pad` stubs exist any more. Run `tools/docker.sh sh -c 'cd tools && python3 test_trailing_pad.py'` for its tests.
- `tools/cc.py` pads each object's `.text` to a multiple of 16 bytes so the original per-object alignment survives the `SUBALIGN(2)` link ([[source-files]]).
- For header checking (T-1200), `tools/check_headers.py` fails when one identifier is declared with different types or declared twice inside one header closure (`include/game.h`, or `include/ovl/<NAME>.h` plus what it includes). Prototypes are checked across return type, parameter types, and `()` against a narrow parameter. `configure.py` makes `build/headers.ok` (target `ninja headers`) an order-only prerequisite of every C compile (T-13500), and `.github/workflows/progress.yml` runs it and `tools/test_check_headers.py` on every run, forks included. See `CODING_STANDARDS.md` section 8a. Since T-3340, `include/main_api.h` was the single declaration file for main-executable symbols, and the same tool ran `tools/sync_protos.py`'s checks. Those checks catch a main symbol declared elsewhere, an overlay view that differs without `MAIN_API_OVERRIDE_<symbol>`, a stale or unguarded override, an overlay header that does not reach `main_api.h`, or a definition whose type differs from `main_api.h`. Its reader of `#include`/`#define`/`#ifdef` is a small preprocessor so an override define hides the `main_api.h` line in that overlay's units. `tools/sync_protos.py` (`--report --write --fix --prune --snapshot --compare`, tests in `tools/test_sync_protos.py`) lists and migrates prototypes, and `tools/dupes.py` writes declarations of copied functions to `main_api.h` for main-executable symbols.
- C headers are listed for Ninja by glob (`include/*.h`, `include/*.inc`), so new headers need no `configure.py` edit.

## Per-object C files (T-0500)

The C files follow the original objects (translation units) so each C object provides its own `.rodata`, emitting jump tables, string literals, and constants from IDO at their original addresses. See [[source-files]] ("Original objects") for boundaries and evidence, and `config/objects/<UNIT>.txt` (`tools/object_boundaries.py --write`) for the data.

- In an overlay layout, there is one `c` subsegment `<NAME>/<addr>` per object (`src/ovl/<NAME>/<addr>.c`, asm in `asm/ovl/<NAME>/{non,}matchings/<NAME>/<addr>/`, object `build/ovl/<NAME>/src/ovl/<NAME>/<addr>.o`), one `.rodata` island `<NAME>/<addr>` per object with `.rodata`, `rodata` asm pieces `<NAME>_rodata_<addr>` for chunks no object owns, and one `data` subsegment `<NAME>_data` covering the remainder of the file after `.rodata`. In the main executable, `src/main/<addr>.c` (`main/<addr>`) uses islands `main/<addr>` and pieces `rodata_<addr>`, while the overlay header stays one per overlay (`include/ovl/<NAME>.h`).
- For migration, run `tools/docker.sh python3 tools/split_objects.py [--dry-run] UNIT...` (`UNIT` is an overlay name, `main/<addr>` for one main file, `main`, or `--all`; requires a split `asm/` matching the current YAML from a finished `ninja` build). It cuts the current C files into top-level pieces (`INCLUDE_ASM` lines, C bodies, `#if` groups, and declarations, with comments attached to the next piece), assigns each function to the object holding its address, and writes one file per object with rewritten `INCLUDE_ASM` folders. It also copies top-of-file declarations into the files that use them (stopping if two objects use one definition with storage) and regenerates `INCLUDE_RODATA` lines. Finally, it adds a prototype to the overlay header (or `include/main_only.h` for `main`) for any C function called across objects without a declaration, writes `config/labels/<UNIT>.txt`, and rewrites the YAML. Then run `python3 configure.py && ninja`. Re-running it is a no-op; on a tree with new C it re-cuts from the current files (tests in `tools/test_objects.py`).
- `INCLUDE_RODATA` lines are generated, never hand-placed, in island objects. An early (non-table) `.rodata` symbol of the chunk may be unreferenced by any function in the object (such as a string reached only through a `.data` pointer table) or declared `extern` by a C function. In either case, the splitter places `INCLUDE_RODATA("<asm_path>/data/<name>.rodata", D_X);` before the function owning the next symbol (or at the end of the file if none). `tools/rodata_pieces.py` writes those pieces. Since T-22007, `rodata_pieces.py` writes a piece for every early island symbol, including those held by a function's own `.s`, so a function converted to C can place string data it must not copy (`func_80142A80`, song text) with `INCLUDE_RODATA` lines. Such a piece is used only once the function's `.s` file is no longer included; an `INCLUDE_ASM` function still carries its own copy.
- Splat names a `.rodata` symbol only when something in the same subsegment points at it, so strings reached through `.data` pointer tables lost their labels when the overlay blob was cut. The generated `config/labels/<UNIT>.txt` lists the `INCLUDE_RODATA` symbols and the YAML's `symbol_addrs_path` reads it, restoring the labels and the `.word D_X` references in `.data`.
- `tools/srcscan.py` (`c_files()`) reads the C files from the YAML files. Downstream tools follow automatically, including `configure.py`, `progress.py`, `queue.py` (where `J` and `S` no longer block in a file with an island), `dupes.py`, `funcdiff.py`, `m2c.py` (`UNIT:func_X` for addresses shared by several overlays), `permute.py`, `trailing_pad.py`, `objdiff.json` (one unit per C file), and CI (unit count from `objdiff.json`). `gen_overlay_configs.py` preserves an existing YAML's subsegments and labels file.
- A trial run of `split_objects.py --all` on a copy of the branch (440 objects, 357 islands, 7 + 637 `INCLUDE_RODATA` lines in `main` and overlays) rebuilt 27 of 27 SHA-1 hashes from a clean `asm/` and was idempotent; RENSYU, OMIMAI, TEL, OLH, and `src/main/80062CD0.c` migrated in the branch itself.
- Under `asm-processor`, a function emits its tables through dummy floats or a dummy switch, requiring enough instructions; `object_boundaries.py` refuses an island when an `INCLUDE_ASM` function is too short (`late_rodata_fits`). No such cases remain because `func_80066A2C` and `func_80066A84` were splat mis-splits whose case blocks had become separate functions, fixed by sizes in `config/symbol_addrs_main.txt`.

## Jump tables and rodata islands (T-1340)

A C `switch` with four or more dense cases makes IDO emit a jump table into the C object's `.rodata`. Because the splat `rodata` subsegment is a single asm blob, that table would land after the blob instead of at the original address, while tables of still-`INCLUDE_ASM` functions remain inside the blob. The build solves this uniformly across the main executable and all overlays (covering 902 jump-table functions: 66 in the main executable and 836 across the 25 overlays that have tables, counted from `%lo(jtbl_` in splat output):

- A dot-prefixed `.rodata` subsegment named like a `c` subsegment, such as `[0x2110, .rodata, RENSYU]` or `{ start: 0x6F3F0, type: .rodata, name: main/80053650 }`, defines a range of `.rodata` that the C object provides. Splat puts `build/.../<name>.o(.rodata)` there in the linker script and writes the range to `<asm_path>/data/<name>.rodata.s` (never assembled). The ordinary `rodata` subsegments before and after it stay asm blobs (`configure.py` reads the YAML for the asm objects via `overlay_data_files()` and regenerates `build.ninja` when a YAML changes). `tools/docker.sh python3 tools/rodata_island.py <yaml> <c name> <function...>` cuts the island for the object that holds the tables of the given functions.
- After every `splat split` (Ninja rule `split`/`osplit`), `tools/rodata_pieces.py <yaml>` appends the island's symbols to the `INCLUDE_ASM` function files `<asm_path>/nonmatchings/<name>/<func>.s` of the first function that mentions them. It uses `.section .rodata` for strings and constants and `.section .late_rodata` for `jtbl_*`. `asm-processor` then places them in compiler order (strings in source order, tables after all strings in function order) and splices the real bytes over its dummy data. When a function is converted to C, it stops including its `.s` and the compiler emits its own table at the right position. Symbols that no function of the file mentions are written to `<asm_path>/data/<name>.rodata/<symbol>.s` and placed with `INCLUDE_RODATA("<asm_path>/data/<name>.rodata", <symbol>);` (printed by the script). `tools/cc.py` lists `INCLUDE_RODATA` files in the depfile alongside `INCLUDE_ASM` files. Both scripts are tested in `tools/test_rodata_tools.py`.
- IDO writes one object's `.rodata` as `[strings and constants in source order][all jump tables in function order][zero padding to 16]`. That ordering holds for a single original object. A C file combining several objects has multiple such chunks, but its compiled object has only one `.rodata`, allowing only one island per C file (the chunk of the object holding the converted functions). Object boundaries appear in the splat output where a table block ends in zero words padding up to a 16-byte boundary. Seventy such boundaries occur across the overlays, while tables that follow each other without zero words belong to one object. `rodata_island.py` stops at those boundaries, refuses functions whose tables are in different objects, and checks 16-aligned start and padded end alignment. A boundary without visible padding (when the object size is already a multiple of 16) makes the island too long, causing SHA-1 to fail until cut by hand in the YAML offsets. Converting tables from a second object of the same file requires splitting the file per object first with `tools/split_objects.py` (which supersedes `rodata_island.py` for migrated units).
- Float and double constants are also late `.rodata` in IDO, which `rodata_pieces.py` does not handle (treating only `jtbl_*` as late, so the SHA-1 check fails if an island holds any). A string literal first used by a converted function and also used by an `INCLUDE_ASM` function is emitted twice, failing SHA-1. A C function that names an island symbol as an `extern` (such as `format(D_800AFBF0)` for a string) leaves the symbol without an owner. Write the literal in C instead (`format((u8 *)"bu00:")`) or place the piece with `INCLUDE_RODATA` in the original position. `migrate_rodata_to_functions: False` is set in the main and generated overlay configs so splat does not copy the symbols into the function files a second time.
- `funcdiff.py` shows relocation and label noise for jump-table functions (where the expected side names `jtbl_*` and `.L*` and the built side uses `.rodata` plus offset), so use the `ninja` SHA-1 check as the final verdict. T-1340 matched main `func_80053DDC` and `func_8007A254` and overlays RENSYU `func_80133E5C`, ETC `func_8014A2C4`, DATE `func_8013EB1C`, DATE2 `func_80133620`, GYOZI `func_8013AE80`, and EVENT `func_8011A874`.

## Data islands (T-9010)

A C object can also provide a range of `.data` so the variables its C file defines land at their original addresses (required for shared `lui $at`; see [[decompile-workflow]] "Data defined in the C file"). This is opt-in per object, like the T-1340 `.rodata` islands.

- `tools/object_boundaries.py --data --write` adds `data`/`bss` lines to `config/objects/<UNIT>.txt` while leaving text and `.rodata` lines untouched (`data <text start> <start> <end> <start ev> <end ev> at:<n>,ref:<m>`). See [[source-files]] ("Data and bss ranges") for the method and confidence rules.
- `tools/data_island.py <UNIT>/<addr>` cuts the range out of the `data` subsegment as `[off, .data, <UNIT>/<addr>]` (followed by `[off, data, <UNIT>_data_<end>]`, or `data_<end>` in `main`) and writes one `INCLUDE_RODATA("<asm_path>/data/<name>.data", D_X);` line per variable into the C file. Splat links `<obj>(.data)` at the island and writes the range to `<asm_path>/data/<name>.data.s` (not assembled).
- After every split, `tools/data_pieces.py <yaml>` (in the `split`/`osplit` rules of `configure.py`) writes `<asm_path>/data/<name>.data/<D_X>.s` with one piece per 4-aligned symbol (IDO aligns every data definition to 4 bytes, as does the `asm-processor` dummy `char[]`). Each piece uses `.byte` lines read from the original file plus `.word SYM` for pointer words splat found so relocations stay intact. It also writes `build/ovl/<NAME>_data_syms.ld` (or `build/SLPM_86.053_data_syms.ld` for `main`) containing `PROVIDE` lines for every island label, which the link rules pass with `-T` so a C definition can replace several splat labels (`D_8015EE34` inside `D_8015EE30`) still referenced by other objects' asm. It fails if an island is not 16-aligned at both ends or a pointer word is unaligned.
- `split_objects.py` preserves data islands by keeping `.data` `INCLUDE` lines and definitions in their file, keeping YAML `data`/`.data` lines, and stopping with an error if a file with an island would be cut into multiple objects.
- Islands must be 16-aligned, so objects whose original data starts unaligned (some TACO and TT objects; see [[source-files]]) get no range. `.bss` islands are not used (overlays have no `.bss`, keeping all their data in the file). A C variable without an initializer goes to `.bss`/common and breaks the layout (failing SHA-1).
- Under T-25005, an object can own more than one `.data` range (for example main `8004F870` owns `800B40F0–800B4390` and the palette at `800E3680–800E36C0`). The first island of an object links `<obj>(.data)`. Each additional island is a dictionary entry with its own section and directory (`{ start: 0x738F0, type: .data, name: main/8004F870, dir: island_800B40F0, linker_section: .data_800B40F0 }`), which `tools/data_island.py` writes when the YAML already has an island of that name. Splat then links `<obj>(.data_800B40F0)` at the range and writes the range to `asm/data/island_800B40F0/main/8004F870.data.s`. `data_pieces.py` writes the pieces of all ranges of an object into the single directory `<asm_path>/data/<name>.data/` so the C file includes them all by the same path. After `cc.py`, `tools/object_layout.py` hands any object with two or more ranges to `tools/data_split.py`. That script cuts the compiled `.data` at the first label of each range into parts, moves each part to its range's section, and moves the symbols with their part. Any reference to unnamed data through the `.data` section symbol (such as IDO's template for a local aggregate initializer) is retargeted to the part's section symbol across `R_MIPS_32` words and `HI16`/`LO16` pairs. Objects with one range or none are untouched. The C file controls the order because IDO emits `.data` in source order and places a function's initializer templates at the function, requiring the parts to sit back to back. Each part must match its range length and leave one part in `.data`, or the build fails. `8004F870.c` defines `D_800E3680` first, then the `D_800B40F0` piece, then `sndisp` (whose `pos[]` template is `D_800B40F8`), and then the rest of the `800B40F0` pieces. Because the section name carries the address, `funcdiff.py --resolve` resolves `.data_800B40F0+8` like a `D_` symbol. Tests live in `tools/test_data_split.py`, `tools/test_data_islands.py`, and `tools/test_object_layout.py`.
- T-9010 verified RPG_BAT `8014E780` (`8015ED90–8015EE90`, 64 pieces) and main `800451D0` (`800B3D60–800B3D80`) byte-identically with the pieces alone and then with C definitions, passing 27/27 on a clean build.

## Orphan strings and hidden object boundaries (T-9400)

An orphan chunk cannot simply be appended to an existing island when its ordering differs from IDO's `[strings][tables][padding]`. TACO `8013DB80` has tables at `8015DA40–8015DA90`, followed by orphan strings at `8015DA90–8015DAA0` used by `func_8013F250`. Merging the ranges into one `.rodata` would place those literals before the tables. A second island with the same C name cannot help because the linker has one input `.rodata` section for that object and cannot select a separate part of it using the single-section model.

The general solution is a hidden text-object split between the users of the two chunks. Confirm a function boundary where no function uses `.rodata` from both sides, split the `object` line in `config/objects/<UNIT>.txt`, assign the orphan range to the new object with `island yes`, remove its `orphan` line, and then run `tools/docker.sh python3 tools/split_objects.py UNIT/<old-address>` and rebuild. T-9400 adds overlay `UNIT/<address>` selection so unrelated source files are kept untouched. Moving functions may require header prototypes or moving file-local declarations; the splitter checks these and the checksum decides. If there is no safe function boundary, the single-section island pipeline cannot own the chunk; keep the function in asm until the object or section model can represent it.

In an isolated Docker trial on TACO (not applied to shared source-owned work), replace `object 8013DB80 80140DF0 8015DA40 8015DA90 yes pad owner` with two lines:

```text
object 8013DB80 8013F250 8015DA40 8015DA90 yes pad owner
object 8013F250 80140DF0 8015DA90 8015DAA0 yes choice/1 owner
```

Remove `orphan 8015DA90 8015DAA0 second_chunk_of_8013DB80`, run `split_objects.py TACO/8013DB80`, configure, and build `build/ovl/TACO.ok`. The trial produced four planned writes, no added prototypes, TACO SHA-1 OK, and both string blocks handed to `func_8013F250.s` in the new island. That trial verified placement for the existing asm and matched C in the file, while the pending C draft still needed its own checksum verification after conversion. The exact historical boundary remains a hypothesis (`choice/1`) rather than a claim about the original source. Queue's `O` flag covers orphan strings as well as tables, even when their C file already has another island.

## Owning orphan chunks with word-aligned text splits (T-10200)

`tools/orphan_rodata.py UNIT` previews ownership changes, and `--apply` writes the object map, C files, and splat YAML through `split_objects.py`. Run it after a build. It uses actual symbol references, preserves each original `.rodata` chunk, and chooses the latest function boundary between the previous chunk's last user and the orphan's first user as a layout hypothesis. All users must belong to one proposed object, and each island must pass the existing ordering checks. Shared users, interleaved references, and unsupported layouts remain orphans with a diagnostic. Strings become ordinary C literals when their user is converted, while unreferenced early pieces use the existing `INCLUDE_RODATA` path.

The old detector required 16-aligned text boundaries. BUNKASAI needs a split at `80154018`, with a second at `80158EB0`. Each corresponding `.rodata` chunk is still 16-aligned. Merging the table-only chunks loses their internal zero padding, shortening `.rodata` by 16 bytes and failing SHA-1, so keep the chunks separate.

`configure.py` runs `tools/object_layout.py SOURCE OBJECT` after every C compile. If compiler text rounding to 16 bytes exceeds the configured source span, the step removes only that surplus, requiring all removed bytes to be zero and free of non-section symbols or relocations. It changes no instructions or relocation values. Other size discrepancies remain visible to `funcdiff` and the unit checksum. This permits word-aligned source boundaries without changing `cc.py` or its compiler flags. Synthetic coverage lives in `tools/test_object_layout.py` and `tools/test_orphan_rodata.py`. Rebuild the unit and verify SHA-1 after applying, because planning alone does not prove code, table contents, padding, or string placement.

## Incremental compiler dependencies (T-13500)

`tools/cc.py` writes each object's Ninja depfile with the headers actually read by its compiler, alongside the existing `INCLUDE_ASM`, `INCLUDE_RODATA`, and trailing-pad assembly inputs. IDO 5.3 supports `-M` but rejects `-MD`. A compiler adapter runs `-M` on the exact temporary C input and include arguments that `asm-processor` passes to IDO, then invokes the unchanged compilation. This preserves conditional includes, source-local include lookup, and Shift-JIS copies. GCC records filenames from the line markers of its existing `cpp` output, and its `EOVERFLOW` tmpfs fallback preserves those relative paths. Neither compiler's code-generation arguments nor the matching passes change.

The header checker remains a blocking order-only prerequisite of every C object. Its stamp depends on all project headers, source files, and checker implementation files, so source edits also trigger validation. Changing its stamp alone does not invalidate clean objects. The configure generator watches `include/` and `src/` directories to refresh the file lists after additions or removals. Missing directory inputs have phony producers, so directory removal can still regenerate the graph.

A configure co-output, `build/include-files.txt`, records file names under `include/` and `src/` and changes only when membership changes. All C objects depend on it so adding or removing files conservatively recompiles all C to cover new higher-priority include shadows that compiler depfiles cannot record. Ordinary content edits remain selective. Configure uses `restat` so an unchanged inventory does not cause repeated regeneration, and deleting it is recoverable. Assembly macro and prelude inputs remain explicit compile dependencies because C preprocessing does not see the assembler's includes.

Run the regression suite in the Docker image with `python3 -m unittest discover -s tools -p test_build_deps.py -v`. Eleven synthetic Ninja cases use real IDO/GCC compilation and the production configure C and checker edges, with unrelated split, link, checksum, and layout stages replaced by synthetic outputs. They cover source, shared, overlay, nested, and conditional headers, source-local header lookup, missing active headers, Shift-JIS copies, and escaped depfile filenames. They also test ASM/rodata/trailing-pad inputs, failed validation, added source-local and nested include shadows, directory removal, deleted inventories, and no-op regeneration and rebuilds. `tools/test_cc.py` retains the compiler and `EOVERFLOW` regressions.
